## 짧은 기록

- **처음 막힌 지점:** 실행기 앱과 실행하는 JS 코드, 빌드 임시 디렉터리와 설치된 앱 교체를 구분해 물었다. Things의 제목 재검색과 사용자가 선택한 대상의 연결, HTTP·소켓·Unix 소켓, 공통 파일 변경 가드와 trailer도 질문했다. PR #60에서는 기존 명령을 유지하는 것과 Relay 실행 입구를 통일하는 것의 차이, CLI 목록 검사의 목적, 가짜 스크립트 문자열·calls.log의 역할을 물었다. 서로 다른 기술·설명 입력 문제를 개인의 디테일 부족으로 묶지 않는다.
- **설명 추가 없이 바로 연결한 지점:** 앞선 설명을 바탕으로 JS 내부 코드만 바뀌는 경우 실행기 앱 재빌드가 불필요하다고 퀴즈에 재진술했다. 소켓 연결 설명을 커넥션풀과 연결해 HikariCP 비교를 요청했다. 공통 파일·업그레이드 예외의 표를 보고 예외와 일반 가드 통과를 나눠 재진술했다. PR #60에서 과외냥이가 사용자 의도를 미리 합리화하자 실제 차이를 설명해 달라고 바로잡았다. 마지막에는 PR 본문을 경우별로 쓰고 읽는 방식이 ATDD와 비슷하지 않은지 스스로 연결했다. 모두 앞선 문답이 있는 상황이며 도움 없는 새 사례 시험으로 세지 않는다.
- **설명·외부화 뒤 달라진 점:** 공통 파일과 우리 전용 파일이라는 소속을 가까이 밝혀주는 설명, 예외를 나누는 표에 강한 긍정 반응이 있었다. PR #60의 목록 검사는 새 CLI를 만들고 Relay 연결을 빠뜨리는 사건과 연결한 뒤 이해했다고 했다. 실제 Relay 서버와 가짜 외부 실행 스크립트를 나누고, 별도 프로세스의 호출 횟수를 파일로 기록한다는 설명을 이어갔다. 이후 테스트의 실패 응답·실제 실행 0회·오류 및 로그의 값 노출 검사를 함께 읽으며 테스트 공부가 재미있다고 밝혔다. “서버 stub”이라는 재진술은 실제 서버는 띄우고 외부 스크립트만 대체한다는 구분으로 교정했다.
- **아직 미관찰이거나 다음에 확인할 점:** 별도 새 사례 독립 적용·지연 후 유지·모기의 직접 테스트 작성은 미관찰이다. PR #60 시험을 읽었지만 실행하지 않았고 server.test.js 전체 완독으로 기록하지 않는다. 모든 보안 경로를 검증하거나 제품 변경 완료를 확인한 것이 아니다. 남은 질문은 아래 보존하며 자동 퀴즈·추가 실험 과제로 만들지 않는다.

## 학습 마찰·재확인·새 발견

### 테스트 독해를 모기가 직접 선택함

모기는 “이 pr의 테스트코드랑 테스트코드 구조?같은거보고싶어”라고 요청했다. 순수 계획 함수의 단위 테스트는 mocking 없이 함수를 직접 호출한다는 점, 서버 시험은 실제 Unix 소켓과 자식 프로세스를 사용하되 Things 실행만 가짜 파일로 교체한다는 점을 나눴다. 가짜 JS 문자열은 임시 파일에 저장되어 실행되며 calls.log의 한 줄은 실제 호출 횟수를 남기기 위한 것이라고 설명했다.

Spring의 자동 테스트 환경과 비교하면서 Node에도 mock 도구가 있지만 이 시험은 프로세스 경계를 실제로 통과시키려는 구조라고 설명했다. Node에 그런 도구가 없어서 수작업이 필수라는 인상을 바로잡았다. 이 설명 뒤의 흥미를 테스트 설계 전체 숙련도 판정으로 넓히지 않는다.

### 과거 ATDD 경험과 현재 경우별 리뷰의 연결

모기는 과거 수업 저장소 [step4](https://github.com/samkimpepper/atdd-subway-fare/tree/step4)를 보여줬다. path.feature, PathStepDef.java, CucumberTest.java, DistanceFareChainTest.java를 읽었다. 경로 기준·나이에 따라 기대 결과가 달라지는 시나리오와 실행 코드의 연결을 설명했다. 이 프로젝트의 SpringBootTest DEFINED_PORT는 실제 앱을 테스트용으로 띄우는 설정이며 가짜 서버 생성과 구분했다.

Cucumber의 현재 유지보수와 ATDD·BDD의 목적을 공식 자료로 조사했다. 활성 개발과 업계 채택률 증가를 구분하고, 이번 조사로 증가·감소 추세를 단정하지 않았다. 모기는 PR 본문에 경우별 섹션을 요구하는 자신의 방식과 연결했다. 과외냥이는 사례 중심 리뷰라는 공통점과 구현 전에 인수 조건·시험으로 개발을 이끄는 ATDD의 시점 차이를 설명했다. 후속 독립 적용은 관찰하지 않았다.
