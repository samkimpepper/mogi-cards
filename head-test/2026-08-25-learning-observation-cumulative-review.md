## 2. 이번 구간의 결론

이번 구간에서 가장 분명해진 것은 설명의 시작점과 이해의 연결·사용감이 함께 달라졌다는
점이다. 정확한 행·관계·조건 분기를 먼저 고정한 PR #524 문답에서는 모기가
설명 뒤 상태 변화를 연결했고, 사용자 사건부터 시작한 코드 독해 형식에는 “아주
맘에든다”고 명시적으로 평가했다. 반면 PR #529에서는 파일·마이그레이션·테스트 구조가
앞선 설명 뒤에 불만족·거슬림·불안이 남았다.

이 대비만으로 PR #529의 마찰 원인을 하나로 확정할 수는 없다. `SCRATCHPAD.md`에 막힌
지점이 없었던 점, 과외냥이가 설명 범위를 일찍 닫은 점, 리뷰·검증 완료를 안심 근거로
제시한 점도 함께 있었기 때문이다. 다만 이미 효용이 확인된 `사용자 사건 → 상태 변화 →
구현 근거` 순서를 채팅 설명에도 일관되게 적용할 이유는 충분하다.

모기의 자기조절은 이번 구간에서도 반복 관찰됐다. 설명의 전제를 교정하고, 한 사건을
곧바로 영구 규칙으로 만들지 않도록 제동을 걸고, 문서 위치를 바로잡고, 피로하거나 필요한
범위를 채웠을 때 스스로 종료선을 정했다. 이는 설명을 수동적으로 받아들이는 모습과
반대되는 관찰이다. 별도의 새 사례 적용은 이번 네 기록에서 시행하지 않았으므로 전이
결과는 `미관찰`로 둔다.

## 3. 세 축별 변화와 근거

### 3.1 설명 입력의 품질

**변화:** 정확한 데이터 대상과 사용자 사건을 먼저 고정했을 때 연결이 이어지는 패턴이
재확인됐다. 동시에 이 순서를 놓친 설명에서는 기술적으로 맞는 내용을 전달하고도 사용감
마찰이 남을 수 있다는 사례가 추가됐다.

**효용이 다시 관찰된 방식:**

- `swatches` 한 행과 그 자식 `swatch_media` 여러 행을 구체 값으로 나눠 URL 이중 저장과
  관계 방향을 설명함.
- `media_id = OLD.id`인 확정 관계와 URL 문자열만 같은 추론을 별도 분기로 나눠 manual
  보호 범위를 설명함.
- 기존 이미지 행의 내용물을 바꾸는 것과 대표 포인터를 다른 행으로 옮기는 것을 분리함.
- 수동 지정·해제를 사용자 사건으로 먼저 보여준 뒤 상태 변화, 테이블·컬럼, 구현·raw
  diff, 테스트 순서로 내려가는 story-first 형식을 사용함.
- SQL 픽스처의 순차 상태 검증과 shell 하네스의 동시성 재현을 서로 다른 역할로 나눔.

**입력 품질이 흔들린 사례:**

- `현재 대표 자리를 비운다`, `선택한 사진의 부모 발색`, `E3`처럼 압축된 표현은 어느
  행·관계·시점인지 다시 풀어야 했다.
- PR #529 설명은 사용자에게 일어나는 사건보다 파일·마이그레이션·테스트 구조를 먼저
  펼쳤고, 설명 뒤에도 불만족이 남았다. 이것이 단독 원인인지는 미확인이다.
- 테스트·리뷰가 완료됐다는 사실은 구현 검증의 근거이지, 모기가 막힌 문구가 해소됐다는
  근거는 아니었다.

### 3.2 모기의 자기조절

**변화:** 필요한 설명 형식뿐 아니라 규칙의 강도, 문서 위치, 세션 범위까지 직접 조절하는
행동이 구체적으로 관찰됐다.

**근거:**

- 같은 원인의 재등장을 기억해 새 정책 발견과 기존 미결 문제를 구분했다.
- 중복 메모 한 건을 곧바로 영구 규칙으로 만들지 않고 prospective 3건 파일럿을
  제안했으며, 제품 설계 카드와 과외 하네스의 저장 위치도 구분했다.
- raw diff의 조건 이동을 읽고 manual 행도 확정 관계라면 삭제된다고 바로 연결했다.
- story-first 문서에 절별 메모를 남기고 설명 형식의 채택 여부를 직접 평가했다.
- 이미 공부한 노트를 `reviewed` 상태만 바꾸지 않은 것이라고 바로잡았다.
- PR #527·#529에서는 모든 SQL 세부를 다 이해하려 하지 않고 필요한 E3~E5 역할까지
  확인한 뒤 종료선을 정했다.
- `SCRATCHPAD.md`를 쓰지 않았어도 채팅에서 막힌 문구와 설명 사용감을 직접 알렸다.

이 기록은 특정 보조물을 반드시 사용해야 한다는 근거가 아니다. 파일 메모가 없을 때도
채팅의 짧은 `?`, 원문 인용, “이게 뭐지” 같은 표시를 막힘 입력으로 받을 수 있다는
근거에 가깝다.

### 3.3 새 사례 적용

이번 네 기록에서는 이름이나 값이 다른 별도 새 사례를 시행하지 않았다. 따라서 새 사례
전이는 `미관찰`이다.

다만 원문 안에서 설명 추가 없이 연결한 사례는 있었다. raw diff의 조건 이동으로 manual
행의 삭제 여부를 판단했고, 과거 대표를 캐시해 되감기보다 살아 있는 후보에 자동 선정
규칙을 다시 적용하는 이유를 연결했으며, PR #529 변경을 `shade_slug` 컬럼과 그 소비처를
함께 제거한 일로 먼저 접었다. 이것들은 해당 PR 문맥 안의 연결이며 별도 사례 전이로
부풀려 세지 않는다.

## 4. 기존 미관찰 항목 정리

| 기존 항목 | 분류 | 이유 |
|---|---|---|
| story-first 형식을 다른 PR 코드 학습 노트에 적용했을 때의 사용감 | 자연 관찰 | 다른 PR에서 실제 노트를 만들 때 보면 충분하다. 이를 확인하려고 비교본을 따로 만들지 않는다. |
| 이름이나 값이 다른 별도 사례 적용 | 종료 | 이전 누적 검토에서 이미 일부 자연 적용을 관찰했다. 이번 구간에 시행하지 않았다는 이유로 다시 과제로 승계하지 않는다. |
| 발견물 중복 확인 관문의 prospective 실행 | 자연 관찰 | 실제 발견물 후보가 생길 때 파일럿 문서에서 집계할 항목이며 과외 질문으로 만들지 않는다. |
| ROI 폐기·대표 포인터 분리의 구현과 UAT | 종료 | 제품 구현·검증 추적 항목이며 학습 관찰로 해소할 대상이 아니다. |
| PR #529 설명 뒤 불만족의 정확한 단일 원인 | 확인 필요 | 원인을 사후 추측으로 확정하지 않는다. 다음 비슷한 설명에서 사용자 사건을 먼저 제시했을 때 마찰이 이어지는지만 자연스럽게 본다. |

`확인 필요`는 모기에게 원인 분석 질문을 추가하거나 별도 실험을 시킨다는 뜻이 아니다.
다음 실제 과외에서 설명 입력을 바꾼 뒤 자연스럽게 드러나는 사용감만 기록한다.

## 5. 다음 세션에서 실제로 바꿀 것

1. **채팅 설명도 사용자 사건부터 시작한다.** 막힌 문구를 받으면 첫 2~3문장에서
   `사용자가 무엇을 함 → 화면이나 저장 상태가 어떻게 바뀜`을 먼저 말한다. 그다음
   필요한 범위에서 `테이블·행·컬럼 → 값의 주인 → 이벤트 전후 → 구현·테스트 근거`로
   내려간다. 파일 목록·마이그레이션 구조·검증 완료 여부로 설명을 시작하지 않는다.
2. **막힘 표시는 가장 가벼운 형태로 받는다.** `SCRATCHPAD.md` 작성을 요구하지 않고,
   채팅의 `?` 한 글자나 막힌 원문 한 줄도 충분한 입력으로 취급한다. 과외냥이는 그
   문구의 생략된 주어·참조 대상·시점을 먼저 확인하며, 리뷰·테스트 통과를 이유로 이해
   설명을 먼저 닫지 않는다.

과거 기록으로 모기가 어디서 막힐지 예단하지 않는다. 위 두 변화는 다음 실제 질문에만
적용하고, 별도 시험이나 하네스 단계로 승격하지 않는다.
