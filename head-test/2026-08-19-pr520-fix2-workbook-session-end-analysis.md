## 4. 현재 가설의 지지 증거와 반박 증거

현재의 좁은 가설은 “같은 사진을 가리키는 URL·key·사본 행·대표 행이 겹치거나, 시작 전 검사·요청 중 상한·함수 전체 마감처럼 시점이 겹칠 때 참조 복원 비용이 생기며, 실제 행·값·이벤트를 외부화하면 상태 전이가 이어진다”이다. 새 제품 정책과 명시된 피로는 별도 설명으로 둔다.

### 지지 증거

1. **C1의 원본과 canonical 사본 분리:** “Storage에 이미 있음”과 “그 발색 namespace에서 소유함”을 분리한 뒤, 모기는 어드민 업로드 원본을 다시 받아 발색별 사본으로 올린다고 재진술했다.
2. **C2의 지속 가능한 외부화:** 모기는 긴 채팅 답변을 파일·한줄·체크박스 구조로 바꿔 달라고 직접 요청했다. 생성된 [`fix2 한줄읽기 워크북`](../temp/2026-08-18-pr520-fix2-line-by-line.md)을 읽으며 체크하고 질문을 메모했다고 명시했다. 이는 주관적 사용성 평가와 실제 사용 관찰이며, 다른 형식과의 통제 비교는 아니다.
3. **C3의 저장 단위 재진술:** `object_key`와 bucket을 분리한 뒤, 모기는 파일명은 그대로이고 공개·숨김 버킷 사이를 이동한다고 정확히 재진술했다.
4. **C4의 새 숫자 적용:** `10초 - 예약 1초 - 경과 3초` 사례에서 모기는 `6초`를 계산했다. 이어 시작 전 검사만으로 부족하다는 방향과 1.2초 요청 상한을 연결했다. 설명에서 fix2의 고정 1.2초와 fix3·fix4의 남은 시간 재계산을 추가로 분리할 필요는 있었다.
5. **C5의 화면·표·결과 분리:** `swatches`, `swatch_items`, `swatch_media`, 격리 RPC와 `SheetManager`를 명시한 뒤, 모기는 fix2 전 `{}` 빈 화면과 fix2 후 전체 판정 보류를 구분했다. 12개 중 일부만 보여주는지 재질문한 뒤 “다 보여주는 건 아님”으로 경계를 고정했다.
6. **C6의 인과 방향 교정:** `대표를 내려서 파일 삭제`가 아니라 `발색에서 사진 제거→사본 대장 삭제→그 사본에 기대던 자동 대표 정리`라는 시간선을 제시한 뒤, 모기는 원인 방향을 이해했다고 명시하고 다음 조건 질문으로 이동했다.
7. **C7의 질문이 실제 제품 경계를 발견:** 같은 사진 URL을 두 `swatches` 행이 갖는 경로를 의심해 코드와 QA 데이터를 확인하게 했다. QA에는 현재 중복 0건이었지만 self-thread 부모 사진 병합으로 정상 UI에서 도달 가능한 경로가 확인됐고, 모기는 이를 #520 코드 수리가 아닌 별도 제품 설계로 분류했다. 이는 이해 실패가 아니라 입력 전제 검증과 새 설계 질문이다.
8. **마지막 적용 질문의 경계:** URL 폴백 SQL을 raw diff로 본 뒤 새 사례 질문을 제시했지만 답을 받지 못했다. C8에서 피로와 중단이 명시됐으므로 이 사례의 전이 성공 여부는 `미관찰`이다.

### 반박 증거

반박 증거는 0개가 아니다.

1. **C1은 용어와 구조가 실제로 어긋나기 쉬움:** “우리 Storage 사진을 다시 다운로드한다”는 문장만으로는 동일 파일 재업로드의 목적이 드러나지 않는다. 핵심은 다운로드가 아니라 `swatch/<발색id>/…` namespace에서 새 소유 사본을 만드는 것이었다.
2. **C4는 최초 재진술이 핵심 방향을 이미 포함:** 시작 전 0.1초가 남으면 긴 요청을 시작해버린다는 문제를 모기가 먼저 구성했다. 추가 교정은 1.2초가 성공 보장이 아니라 중단 상한이며 최종 공통 마감은 fix3·fix4까지 이어졌다는 범위였다.
3. **C5는 합리적인 부분 성공 질문:** `swatches` 12행을 읽었고 `swatch_media`만 실패했다면 안전한 2~3행이라도 보여줄 수 있는지 묻는 것은 자연스럽다. 실제 계약이 격리 대상을 확정할 수 없어 전체 오류를 택했음을 설명해야 했다.
4. **C6은 `회수`·`삭제`의 중의성과 워크북 전제 누락:** 문서는 대표 행 회수와 Storage 객체 삭제를 가까이 놓았고, 어떤 사용자 이벤트가 먼저 사본 삭제를 일으키는지 충분히 앞에서 고정하지 않았다. 인과 반전은 입력 품질로도 설명된다.
5. **C7은 실제 미결 제품 정책:** 발색샷 계정마다 self-thread 사용 방식이 다르다는 모기의 반박 때문에 `트윗 하나`와 `스레드 전체` 중 어느 등록 단위가 옳은지 현재 확정할 수 없다. 망설임을 조건 손실로 볼 수 없다.
6. **C8은 명시적 피로 뒤 중단:** 마지막 SQL 조건 질문의 미응답은 피로와 PR 머지·세션 종료 선택으로 직접 설명된다. 이를 새 사례 전이 실패, 유지 실패, 또는 일반적 기억 문제로 해석할 근거가 없다.

### 잠정 판정

- **컨텍스트 구성 비용 가설:** 부분 지지. 행의 주인·이벤트 방향·공통 종료 시각을 외부화한 뒤 재진술과 새 숫자 적용이 이어졌다. 동시에 여러 재질문은 실제 용어 중의성·계약 선택·새 제품 경계를 드러냈다.
- **외부화 효과:** 지지. 체크박스 워크북을 모기가 직접 요청·사용·긍정했고, [`공통 마감 code diff note`](../code-diff-notes/2026-08-18-pr520-common-deadline.md)로 숫자·raw hunk·fix2~fix4 경계를 고정했다. 통제 비교가 없어 효과 크기와 원인 요소는 미측정이다.
- **일반적 작업기억 저하 가설:** 지지 불충분. 새 숫자 계산, 12행 오류 사례, 원인 방향 교정 후 후속 조건 질문, self-thread 전제 검증이 관찰됐다.
- **질문 횟수를 실패 지표로 쓰는 방식:** 반박됨. 질문이 `{}` 위장 화면의 정확한 소비자, 대표 회수의 인과 방향, 서로 다른 발색의 같은 URL 도달 경로, 후속 제품 설계 필요성을 드러냈다.
- **마지막 미응답:** 피로 뒤 `미관찰`. 정답·오답으로 분류하지 않음.

## 5. 가장 최근 이전 관찰의 다음 예측과 오늘 사례

가장 최근 종료 관찰인 [`2026-08-18-pr520-lifecycle-security-session-end-analysis.md`](./2026-08-18-pr520-lifecycle-security-session-end-analysis.md)는 별도 `다음 세션에서 구분할 예측` 제목을 두지 않고 종료 기록에 미관찰 항목을 남겼다. 그 항목을 이번 대조의 운영상 예측으로 사용한다.

| 이전의 미관찰·다음 확인 항목 | 오늘 판정 | 오늘 근거와 한계 |
|---|---|---|
| 새 이름·값을 넣은 별도 사례 전이 | **혼합** | 공통 마감의 새 숫자에서 6초 계산, 사본 대장 실패 시 12개 목록의 표시 경계 재진술은 관찰됨. URL 폴백 SQL의 마지막 새 사례는 피로 뒤 미응답이라 미관찰. 서로 다른 세 사례를 하나의 성공률로 합치지 않음. |
| 경쟁 조건의 새 사례 전이 | **미관찰** | 이번 구간은 공통 마감, 오류 전파, URL 폴백이 중심이었다. fix3 URL 동시 삭제 직렬화는 설명 재료로만 언급했고 독립 새 경쟁 사례를 풀지 않음. |
| 시간 지연 뒤 유지 | **미관찰** | 세션이 날짜를 넘겼지만 같은 항목을 통제된 지연 뒤 다시 확인하지 않았다. 장시간 세션 자체를 지연 유지 검사로 간주하지 않음. |
| 제품 정책과 DB 규칙의 슬롯 수를 맞춘 비교 | **미관찰** | self-thread 제품 정책과 URL 폴백 SQL을 모두 다뤘지만 슬롯 수와 난도를 사전에 맞추지 않았다. 질문 유형 차이를 도메인 친숙도의 효과로 분리할 수 없음. |

## 7. 짧은 종료 기록

- **처음 막힌 지점:** 같은 Storage 안의 어드민 원본을 왜 다시 복사하는지, fix2의 공통 마감과 1.2초 요청 상한의 범위, `swatch_media` 조회 실패가 어느 화면에서 왜 전체 오류가 되는지, 사진 사본 삭제와 대표사진 회수의 인과 방향.
- **설명·외부화 뒤 달라진 점:** 발색별 canonical namespace를 소유 구조로 재진술했고, 같은 key가 두 버킷 사이를 이동한다고 정리했다. 공통 마감 새 숫자에서 6초를 계산했으며, `{}` 빈 성공과 reject 오류를 구분했다. 사본 삭제→자동 대표 정리의 방향을 고정한 뒤 URL 폴백의 발색 스코프를 질문했고, 서로 다른 발색의 같은 사진 전제를 검증해 self-thread 제품 설계를 #520 밖으로 분리했다.
- **아직 모르거나 다음에 확인할 점:** 계정별 self-thread 사용 방식이 달라 등록 단위를 트윗 하나와 스레드 전체 중 어느 것으로 둘지 미결정이다. URL 폴백 SQL의 마지막 새 사례 적용은 피로로 미관찰이다. 경쟁 조건의 새 사례 전이, 시간 지연 뒤 유지, 제품 정책·DB 규칙 동급 비교도 미관찰이다.
