# 머가리 테스트 첫 정식 실행 실패 기록 — PR #504

날짜: 2026-08-13

대상:

- 참가자 케이스: [`archive/runner-1.0/cases/2026-08-12-searchpath-pin.json`](./archive/runner-1.0/cases/2026-08-12-searchpath-pin.json)
- reviewer-only 키: [`archive/runner-1.0/keys/2026-08-12-searchpath-pin.answers.json`](./archive/runner-1.0/keys/2026-08-12-searchpath-pin.answers.json)
- 원재료: PR #504 `update_swatch`의 `search_path` 고정
- 러너: `head-test-1.0`

## 판정

**정식 측정 실패·효과 판정 제외.**

초기 블록이 PostgreSQL 사전지식과 기계적으로 생성된 문장 해독을 요구했고, 270초 제한은 그 해독 시간을 포함하기에 지나치게 짧았다. 참가자가 내용 결함을 신고하려 했을 때는 이미 시간 초과로 세션이 `incomplete`에 들어가 신고 버튼도 잠긴 뒤였다.

이 실행은 문단과 표의 외부화 효과, 작업기억 병목, 일반 추론능력 중 어느 것도 측정하지 못했다. 가장 강하게 관측한 것은 **케이스 제작 실패와 종료 후 주석 경로 부재**다.

PR #504 소재는 이미 노출되고 해설까지 진행했으므로 새 정식 측정에 재사용하지 않는다.

## 원래 측정하려던 것

가설은 여러 주체·값·이벤트·전후 상태를 문단으로 유지할 때보다 표로 외부화했을 때 모기의 추론이 안정되는지 보는 것이었다.

이번 PR의 실제 변경 핵심은 매우 작다.

```text
update_swatch의 호출자 권한과 함수 본문은 유지
→ 함수의 search_path만 public으로 고정
→ 나중에 고정이 풀리면 구조 검증이 CI를 실패시킴
```

그러나 참가자 케이스는 이 핵심만 제시하지 않고 다음 주변 맥락까지 한 초기 블록에 넣었다.

- `pg_proc.proconfig`
- 호출자 `search_path`와 동명 객체 탐색
- `SECURITY INVOKER`와 RLS 권한 경계
- `ALTER FUNCTION`과 본문 사본 방지
- `NOTICE`에서 `EXCEPTION`으로의 판정 승격
- `RESET search_path` 롤백
- SECURITY DEFINER 함수만 싣는 정책 스냅샷의 관측 범위

이 항목들은 PR의 안전성 설명에는 관련 있지만, 한 줄짜리 속성 변경을 처음 이해하기 위한 최소 입력은 아니다.

## 실제 진행 순서

### 1. 참가자 케이스 준비와 시작

마스터가 참가자 케이스와 정답 키를 분리해 만들고 validator를 통과시켰다. WSL2 파일 선택의 불편을 줄이기 위해 러너에 `?case=cases/...json` URL 자동 로드도 추가했다. 해당 데이터는 현재 `archive/runner-1.0/` 아래에 보존돼 있다.

모기는 원본 카드·PR·정답 키를 미리 읽지 않고 정식 케이스를 시작했다. 이 낯섦 조건은 지켜졌다.

### 2. 초기 블록에서 즉시 입력 난도 문제 발생

모기는 진행 중 다음을 보고했다.

> jargon이 너무 심하고 문장의 의도 해석 자체가 안 된다.

> 5분 제한이 너무 가혹한 것 같다.

문항 하나의 답을 모른 것이 아니라 초기 블록의 규칙 문장과 질문 전체가 무엇을 묻는지 파악하기 어려운 상태였다. 따라서 관찰 단위가 “명시된 조건을 유지하고 적용하는가”에 도달하지 못했다. 그 이전 단계인 “생소한 PostgreSQL 용어와 기계 문장의 의미를 복원하는가”에서 시간이 소비됐다.

### 3. 자유 문답 후 제출 방안 제안

모기는 먼저 과외냥이와 자유롭게 질문을 주고받고, 이해한 뒤 HTML에 최종 답을 제출하는 방식을 제안했다.

학습 방식으로는 타당하지만, 현재 프로토콜의 독립 수행 측정에는 사용할 수 없다. 내용 설명을 받은 뒤의 제출은 외부화 효과와 설명 학습 효과가 섞이기 때문이다. 이에 실행을 입력 결함으로 무효화한 뒤 자유 문답으로 전환하는 방향을 안내했다.

### 4. 시간 초과 뒤 신고 경로 차단

안내 시점에는 초기 블록 시간이 이미 끝나 세션이 `incomplete`로 잠겼다. 종료 상태에서는 `입력 결함·내용 도움 신고` 버튼도 비활성화되므로, 참가자가 발견한 문제를 실행 JSON 안에 사후 주석으로 남길 수 없었다.

이것은 상태 머신이 시간 초과 뒤 답변을 막는 데는 성공했지만, **종료 원인과 별개의 사후 관찰을 기록하는 기능은 없다는 UI·기록 결함**이다.

실행 JSON이 실제로 저장됐는지는 이 기록 작성 시점에 확인하지 못했다. 저장됐더라도 현재 스키마에는 아래 참가자 관찰이 들어가지 않는다.

> jargon이 과도하고 문장의 의도를 독립적으로 해석하기 어려웠으며, 문항 4개에 블록당 약 5분은 지나치게 짧았다.

### 5. 종료 후 자유 해설

시간 초과로 정식 측정이 이미 제외된 뒤, 과외냥이가 초기 블록의 용어와 규칙을 평범한 말로 풀었다. 모기는 퀴즈 해설 부분은 보지 않은 채 개념 설명을 읽고 다음을 질문했다.

- 왜 대상 함수는 SECURITY DEFINER가 아니라 INVOKER인가
- 다른 RPC도 모두 같은가
- search_path 고정은 다른 변인을 제거하는 것과 비슷한가
- 기존 검증은 왜 미고정을 오류가 아니라 NOTICE로만 남겼는가

이 질문들은 PR의 핵심에서 벗어난 추론 실패가 아니었다. 참가자 케이스가 설명 없이 전제한 `INVOKER/RLS`와 선재 위생 부채의 처리 방식을 복원하기 위한 선수지식 질문이었다.

### 6. 실제 diff 확인 뒤 핵심을 즉시 식별

모기가 실제 PR diff를 본 뒤 다음과 같이 정리했다.

> 겨우 여기만 수정한 건데, 그냥 search_path가 schema를 정확하게 가리키도록 고정하고 더 볼 것이 없는 것 아니냐.

이 판단이 변경의 핵심에 가깝다. 주변 설명을 걷어내자 모기는 다음 두 가지를 즉시 분리했다.

1. 함수 본문과 권한 구조는 유지한다.
2. `search_path` 속성만 고정하고, 재발 시 검증을 실패시킨다.

따라서 초기 블록의 실패를 “작은 코드 변경의 의미를 이해하지 못함”으로 기록하면 사실과 반대다. **실제 diff보다 테스트용 재서술이 훨씬 어려웠다.**

## 실패 원인 분석

### 1. 최소 필요 지식과 주변 근거를 구분하지 않음

케이스는 PR의 모든 검토 근거를 규칙 5개에 채우려 했다. 그 결과 단순 속성 변경을 이해하는 데 필요하지 않은 권한 모델, 롤백, 스냅샷 범위, CI 승격 역사가 같은 비중으로 제시됐다.

`규칙은 정확히 5개`라는 기계 조건이 작은 PR에도 다섯 개의 개념 덩어리를 요구해, 입력을 줄이기는커녕 부풀리는 압력으로 작용했다.

### 2. 생소한 용어를 먼저 정의한다는 원래 개선안을 지키지 않음

이전 세션에서 정한 개선안에는 필요한 생소한 용어를 먼저 정의한다는 조건이 있었다. 그러나 정식 케이스는 아래 용어를 정의하지 않았다.

- schema와 `search_path`
- 동명 객체와 이름 해석 순서
- 호출자
- `SECURITY INVOKER`와 `SECURITY DEFINER`
- `proconfig`
- `NOTICE`와 `EXCEPTION`

러너 validator는 토큰 역할과 JSON 구조는 검사했지만, 참가자에게 필요한 용어 정의가 존재하는지는 검사하지 않았다.

### 3. typed fact의 구조적 동형성이 읽을 수 있는 설명을 보장하지 않음

러너는 한 typed fact에서 문단과 표를 생성하므로 두 표현의 사실 불일치는 줄였다. 그러나 다음 고정 열을 기계적으로 문장으로 이어 붙였다.

```text
정보 출처 → 값의 주인 → 관측·판단 → 이벤트 → 변경 전 → 변경 후
```

이 구조는 데이터 표에는 쓸 수 있어도 자연스러운 설명 순서와 같지 않다. `값의 주인`, `관측·판단`, `판정 승격` 같은 압축 표현이 주어·행위·인과를 대신하면서 문장의 의도를 읽기 어렵게 했다.

즉 기계는 **표와 문단이 같은 셀을 사용한다는 구조적 동형성**만 보장했고, 문장이 설명으로서 이해 가능하다는 의미적 품질은 보장하지 못했다.

### 4. 제한시간이 추론 외의 비용까지 측정함

한 블록은 270초이고 질문은 네 개였다. 참가자는 그 안에 다음을 모두 해야 했다.

1. 정의되지 않은 용어를 추측한다.
2. 기계 문장을 자연어 의미로 복원한다.
3. 다섯 규칙의 관계를 파악한다.
4. 네 질문의 의도를 해석한다.
5. 구조 입력과 자유서술을 작성한다.

이 시간은 단순히 엄격한 것이 아니라 목표 가설과 다른 비용을 포함했다. 결과적으로 작업기억·외부화보다 도메인 어휘 숙련도와 읽기 속도를 강하게 측정했다.

### 5. 측정 모드와 학습 모드를 분리하지 못함

참가자가 문장의 의미부터 질문해야 하는 상태에서는 독립 측정을 계속할 수 없다. 그러나 현재 러너에는 다음 두 경로만 있다.

- 설명 없이 제한시간 안에 완료
- 중단·무효·시간 초과로 종료

자유 문답 뒤의 적용 능력을 별도로 관찰하는 학습 모드가 없다. 문답 후 같은 실행에 답을 제출하면 측정이 오염되고, 종료하면 학습 결과를 구조적으로 기록할 수 없다.

### 6. 종료 후 사후 주석이 없음

시간 초과 뒤 답변과 판정을 잠그는 것은 맞다. 하지만 다음은 변경하지 않고 추가할 수 있어야 한다.

- 참가자가 뒤늦게 식별한 입력 결함
- 제한시간의 체감과 이유
- 외부 도움을 받기 시작한 시점
- 브라우저·조작 문제

현재는 종료 후 이런 관찰을 JSON에 추가할 수 없다.

## 이 실행이 증명한 것

- URL 자동 로드로 WSL2 파일 선택 문제를 피할 수 있었다.
- 제한시간이 지나면 세션을 `incomplete`로 잠그는 기계 규칙은 작동했다.
- 종료 뒤 답변을 계속 제출하거나 정상 완료로 위장하는 경로는 UI에서 차단됐다.
- validator 통과는 참가자가 이해할 수 있는 입력 품질을 증명하지 않는다.
- 같은 사실을 쓴 문단과 표를 자동 생성해도 자연어 설명 품질은 별개다.
- 실제 diff보다 추상화한 테스트 재료가 더 어려워질 수 있다.

## 이 실행이 증명하지 않은 것

- 모기의 전반적 추론능력이나 지능
- 작업기억 또는 컨텍스트 유지 병목
- 문단 대비 표 외부화의 효과
- 표를 제공했을 때의 회복 여부
- 지연 후 독립 적용 능력
- PR #504 변경에 대한 최종 이해도
- 270초가 일반적으로 짧은지, 이번 입력에만 짧았는지

## 다음 정식 실행 전 필수 수정

### P0. 케이스 제작 규칙

1. **diff 핵심을 먼저 한 문장으로 쓴다.** 그 문장을 이해하는 데 직접 필요한 사실만 측정 규칙에 넣는다.
2. 작은 PR을 맞추기 위해 규칙 수를 억지로 5개로 늘리지 않는다. 현재의 `정확히 5개` 계약을 재검토한다.
3. 권한 근거, 롤백, 스냅샷 범위, 과거 사고 같은 주변 검토 맥락은 핵심 추론에 필요할 때만 넣는다.
4. 참가자에게 생소할 가능성이 있는 용어를 측정 전에 중립적인 glossary로 정의한다. glossary는 A/B 양쪽에 동일해야 하며 정답이나 추론 방향을 암시하지 않는다.
5. 케이스 작성자가 아닌 사람이 시간 제한 없이 먼저 읽고, 각 문장의 주어·대상·이벤트를 설명 요청 없이 식별할 수 있는지 확인한다.
6. 실제 diff보다 테스트 설명이 더 길고 어려우면 정식 케이스를 만들지 않는다.

### P0. 시간 규칙

1. 읽기·용어 해독 시간과 답변 시간을 한 숫자로 묶지 않는다.
2. 다음 pilot 전에 소리 내어 읽기 또는 비참가자 dry run으로 현실적인 시간을 측정한다.
3. `4~5분`을 가설에서 나온 필수값처럼 취급하지 않는다. 시간 제한은 조급함을 만드는 장치가 아니라 무한 세션을 막는 상한이어야 한다.
4. 시간 부족 신호가 나오면 자동 timeout 전에도 입력 결함 또는 피로 중단으로 전환할 수 있도록 진행자가 관찰한다.

### P1. 러너

1. terminal phase를 바꾸지 않는 `post_run_note`를 추가한다.
2. 시간 초과 화면에서도 입력 품질·조작 문제·외부 도움 시점을 사후 주석으로 기록할 수 있게 한다.
3. `incomplete`와 `invalidated` 중 하나만 고르는 대신, 주 종료 상태와 관찰 태그를 함께 보존한다.
4. 정식 측정과 별개로 자유 문답 후 적용을 기록하는 `study mode`를 설계한다. study mode 결과를 A/B 독립 수행 결과와 합산하지 않는다.

## PR #504 처리 원칙

- 이 소재로 정식 head-test를 다시 하지 않는다.
- 이후 문답은 일반 과외·코드리뷰 학습으로 취급한다.
- PR 승인 판단은 실제 diff와 검증 근거를 기준으로 별도로 진행한다.
- 이번 timeout과 질문 이력을 PR 이해 실패나 머지 불가 근거로 사용하지 않는다.
- 모기의 핵심 재진술은 `호출자 권한은 유지하고 search_path만 public으로 고정하며, 재발하면 CI가 실패한다`로 기록한다.

## 다음 실행을 위한 최소 통과 질문

새 케이스를 시작하기 전에 제작자 또는 독립 검토자가 아래에 모두 `예`라고 답해야 한다.

- 실제 변경 핵심을 한 문장으로 말할 수 있는가?
- 모든 측정 규칙이 그 한 문장을 이해하거나 적용하는 데 직접 필요한가?
- 참가자가 모를 수 있는 용어를 정답 누설 없이 먼저 정의했는가?
- 기계 생성 문장을 사람이 자연스러운 설명으로 검토했는가?
- 제한시간을 비참가자 dry run으로 확인했는가?
- 입력 결함이 발견되면 timeout 전후 모두 기록할 수 있는가?
- 실패 결과를 모기의 능력과 입력 설계 문제로 분리해 해석할 수 있는가?
