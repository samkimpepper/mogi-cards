## 학습 마찰·재확인·새 발견

### story-first는 이번에 가장 중요했던 설명 피드백

> 좋다옹ㅋ 이번세션은 흠 story-first만 잘 보존됐다면 좋았을것같다옹 ㅜㅜ 그게 제일 중요한데 어느새부턴가 과외냥이 네가 안그러더라고 문서구조에 문제가있나?ㅠ

> 흐으음 그러니까 내가 설명한건 예시라옹 약간. story-first로 해달라는거였어 sent:true로 한 맥락을 설명해달란거였어

모기는 변경 값부터 말하지 말고 어떤 요청에서 무엇이 정상이며 왜 일부러 바꿔 시험하는지 먼저 설명하라고 요구했다. 과외냥이는 이를 한때 특정 sent 사례의 보충·옵션 표기 문제로 좁혀 적었다가 모기의 정정 뒤 기존 전달 메모를 고쳤다. 사용자 예시를 일반적인 설명 요청과 구분하지 못한 응답 문제다.

문서 판독 결과 story-first는 기존 프리앰블과 최신 누적 검토에 이미 있었다. 표·코드·운영 절차와 핵심 원칙이 같은 문서에 섞여 있었지만, 이것이 이번 실패의 단일 원인이라는 실험 근거는 없다. 모기가 정리를 명시적으로 요청해 `7fec08a`에서 AGENTS·프리앰블 상단으로 원칙을 옮기고, 사건 설명 뒤 표·코드·판독 근거를 놓도록 맞췄다. 시작 훅이 새 순서를 전달하는 것은 직접 확인했으며 실제 설명 효과까지 검증한 것은 아니다.

### 본문 버전 2 선호와 제작 방식은 분리해 보존

> 난 본문 버전2가 훨씬ㄴ맘에들어

모기는 제작 방식을 알기 전에 2번을 골랐다. 최종 본문 작성자는 둘 다 레포를 못 봤고, 차이는 앞단에서 내부 워커가 직접 맥락 26곳을 고른 A(버전 2)와 제한된 독자가 제시한 17곳만 내부 워커가 보충한 B(버전 1)였다. 과외냥이는 해당 계약과 [측정 기록](../../todo-ops/docs/measurements/2026-10-23-reader-ab.md)을 읽고 이 조건을 구분했다. transcript 격리를 독립 감사한 것은 아니다.

버전 2는 모기의 쿠폰 예시와 Stryker 변이, 잘못된 결과와 에이전트 보고, 측정 결과와 보강 후보를 해당 사건 안에서 연결했다. 이것이 선호에 영향을 줬을 것이라는 해석에 모기가 동의했다. 그러나 코드 접근·과제 범위·재료 양·재작성자의 선택이 함께 달라 원인을 분리하지 못했다. 읽기 선호를 기술적 정확성 우위로도 해석하지 않는다. 최신 실험 기록에는 A의 초기 오류 지적이 후속 재현에서 정정된 사실도 있다.

모기는 예상한 쪽이 아니어서 실망했다고 밝히고 몇 번 더 비교하겠다고 했다. 제한된 독자 방식이 성공·실패했다고 확정하거나 즉시 도입하지 않았다. 과외냥이는 이 실험을 새로 실행하지 않았다.

### 현재 학습 맥락의 전달과 하네스 추가 중단

모기는 에이전트에게 자신에 관한 정보를 더 주고 싶다고 했고, 현재 읽기 목적·설명받은 범위·실제 선호 예시를 정리해 보내 달라고 요청했다. 기존 독자 소개는 A·B가 이미 공유했으므로 이번 차이를 개인 정보의 양 부족으로 단정하지 않았다. 성격·능력 프로필을 만들거나 모기에게 매번 장문의 자기소개를 요구하지 않았다.

관련 대화·비교 조사·전달 상태는 [단일 마스터 메모](../master-delivery-memos.md)의 2026-10-23 PR #11 절에 보존했다. 최초 전송은 주소 불일치로 보류했고, 같은 자기 터미널·Run과 갱신된 투두냥 주소를 확인한 뒤 `msg_5cfa0a24a87d`를 전송했다. 후속 학습 맥락·비교 조사는 `msg_c289084adeb0`로 보냈다. 두 메시지는 전송 접수만 직접 확인했으며 담당자의 읽음·인수 회신은 이 과외에서 확인하지 않았다.

당분간 하네스 개선·설명 도구 추가를 멈추고 기존 것들을 활용하자는 요청은 [최신 누적 검토](./2026-10-22-learning-observation-cumulative-review.md)에 남겼다. 이후 모기가 명시적으로 요청한 story-first 문서 정리는 위의 한정된 변경이다. 이번 종료 절차에서 추가 지침·도구·프로필·파일럿을 만들지 않는다.
