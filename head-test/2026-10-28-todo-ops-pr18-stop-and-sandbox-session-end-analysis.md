## 짧은 기록

- **처음 막힌 지점:** LOCAL.md가 없는 상황이 우리 설치에서 어떻게 생기는지, STOP 생성 주체·채팅 트리거·발견 시점·정리 보장, worker-abandon의 동작을 물었다. stderr 출력 자체를 실행 실패와 연결해 물었고, 경고를 stderr로 옮기는 가상의 잘못된 수정을 실제 변경 제안으로 읽었다. 후반에는 샌드박스가 무엇인지, 누가 어떻게 제한을 거는지, guard와 어디서 다르게 막는지, 같은 파일의 정상 최신화와 임의 편집을 구분할 수 있는지를 물었다. 앞선 설명에 생략된 주체·가정·적용 범위를 포함하는 질문들이며 하나의 개인 원인으로 묶지 않는다.
- **설명 추가 없이 바로 연결한 지점:** 앞선 설명을 받은 상황에서 “orca-wait만 쓰면 완료메시지못보내는 워커가 죽은거는 모르니까”라고 필요성을 직접 재진술했다(Turn 16). 충돌 표식 밖의 코드에서도 설정 전달 문제가 생길 수 있다는 방향을 요약했고(Turn 19), 파일 내용 수정이 아니라 읽을 경로의 덮어쓰기라는 부분은 바로 교정받았다. STOP을 만드는 사람을 모기로 가정한 근거를 되묻고, 지금 과외 자체가 기능 사용 방식을 검토하는 과정이라고 설명의 전제를 바로잡았다(Turn 11·13). 셸 문자열 오류가 반복된다는 공통점을 짚고, 리뷰 횟수 확대 외의 방법·기존 공개 구현을 찾아 달라고 요청했다. 이 연결들은 앞선 설명·리뷰가 있는 맥락이며 도움 없는 독립 해결로 세지 않는다.
- **설명·외부화 뒤 달라진 점:** stderr와 종료 코드를 나누고, 경고 통로를 바꾸는 상황은 시험의 탐지력을 설명하기 위한 가정이라고 밝힌 뒤 “아 이제 완전이해감”이라고 했다(Turn 23). STOP의 역할을 설명받은 뒤 loop에 해당한다는 범위는 재진술했지만(Turn 28·35), 마지막 요약에는 읽는 주체와 종료 보장의 혼동이 남아 재정정했다. 샌드박스는 OS가 실제 쓰기를 막았다는 결과를 자기 말로 연결하면서도 개념은 모른다고 분리해 밝혔다(Turn 46). `chmod` 비교 뒤에도 제한을 거는 과정을 다시 물었고, 시작할 때 정책을 붙이는 흐름과 실제 접근 시점을 설명한 뒤 다음 단계로 가자고 했다(Turn 49). 이는 그 설명을 받아들였다는 반응이며 정책·호출 과정을 독립적으로 재진술한 증거는 아니다.
- **아직 미관찰이거나 다음에 확인할 점:** STOP 판정·작업 배정 정리·프로세스 종료의 차이를 교정 없이 다시 설명하는지, 샌드박스 경계를 새 사례에 적용하는지, 지연 후 유지되는지는 미관찰이다. 모든 리뷰를 독립 판정했거나 PR 전체를 완전히 이해했다고 기록하지 않는다. 제품 최신화 자동화의 편의와 권한 분리를 고민했지만 직접 설계를 구현·검증한 것은 아니다. 후속 실험은 담당자 경로에서 진행 중이라는 사용자 보고만 있으며 이번 세션에서 그 결과를 보지 않았다. 이 항목들을 해소하려고 다음 세션에 퀴즈·추가 실험을 의무 삽입하지 않는다.

## 근거·전달·종료 범위

- 과외 중 STOP 유무에 따른 loop-check 출력, 공백 경로의 작은 셸 예제는 임시 환경에서 직접 실행했다. 실제 워커 중단·새 워커 실행·제품 수정은 하지 않았다. 후반의 sandbox 쓰기 차단·정상 작업 실패는 담당자의 실험 보고를 읽은 결과이며 과외냥이의 재실행과 구분한다.
- 담당자의 실험 결과는 “Bash만 제한한 조건에서 어떤 일이 있었나”의 근거다. 이를 전체 프로세스 격리도 Edit/Write를 막을 수 없다는 결론으로 일반화하지 않았다. 외부 Orca 위임 쓰기·워커 적용은 당시 미실측이었다. 잘못된 설정의 경고를 stream-json에서 못 본 것과 경고 자체가 없다는 주장도 구분해 메모에 남겼다.
- 발견·질의·회신은 [마스터 전달 메모](../master-delivery-memos.md)에 보존했다. 최종 재사용 제안 `msg_9855bf69a2f7`에 동일 본문의 회신 두 개를 받았고 읽음 확인했다. 담당자는 전체 격리 실험 `td-xfp.4`, 최신화 전용 실행기 `td-xfp.5`, 차분 시험·파서 교체 보류를 보고했다. 당시에는 기록만 된 계획이며 “투두냥만 실행” 강제 방법은 미정이었다. 종료 요청의 “그거 진행하고있다옹”은 진행 보고로 보존하고 완료·안전성 검증으로 바꾸지 않는다.
- 10월 22일 누적 검토에서 인수한 질문 범위·전제 명시와 적합한 표현 선택을 적용했다. STOP 생성 주체를 먼저 가정한 설명, stderr로 옮기는 가정을 실제처럼 들리게 한 설명, OS가 막는다는 말만 하고 제한 부여 과정을 빠뜨린 설명, 최신화를 빼면 사용자가 직접 해야 한다고 좁힌 설명은 재정정했다. 설명을 들은 뒤의 긍정 반응과 모기의 독립 재진술을 합치지 않는다. 새 설명 도구·하네스·추가 누적 검토는 만들지 않았다.
- 종료 이벤트 파일럿 조회는 `due: []`였다. 카운터 미정 경고를 실행 지시로 취급하거나 파일럿 횟수를 추정해 올리지 않았다. 이번 종료 기록까지 최근 누적 검토 이후 종료 기록은 3개라 새 누적 검토를 만들지 않는다.
- 종료 기록 작성 전 SCRATCHPAD의 세션 구간과 개인 보존 구간을 모두 읽었다. 둘 다 비어 있고 제목도 이미 `[다음 PR]`이므로 변경할 내용이 없다. 기존 reviewed 상태를 바꾸지 않는다.
- 종료 관찰과 대화 원문은 별도 커밋하고 공책을 push한다. 이전 세션 종료 응답이 자동 append된 raw도 함께 보존한다. 이전 명시적 제외 대상인 PR #51 로컬 코드 노트·모기 답안은 그대로 미커밋 상태로 둔다. 현재 종료 응답과 도구 기록은 Stop 훅이 뒤이어 append하는 원문이며 당시 존재하지 않는 원문을 미리 재구성하지 않는다. 제품·운영 저장소에는 쓰지 않는다.
