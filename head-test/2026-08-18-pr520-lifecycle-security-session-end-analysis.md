## 4. 현재 가설의 지지 증거와 반박 증거

현재의 좁은 가설은 “비슷한 이름이 서로 다른 저장 단위·실행 주체·시점을 가리킬 때 참조 복원 비용이 생기고, 테이블 행과 이벤트 전후를 나눠 외부화하면 상태 전이가 이어진다”이다. 오늘 명시된 피로와 새 보안 지식의 영향은 별도 설명으로 둔다.

### 지지 증거

1. **C2의 시간축 분리:** `pending_upload → 사용자 숨김 → Storage 업로드 성공 → mark_stored → hidden_at 재검사 → revoke 기록`을 순서로 고정한 뒤, 모기는 기존 트리거가 놓친 이유를 `object_key = NULL`과 연결했다.
2. **C3의 실행 주체 분리:** `swatch_media_lifecycle_queue`를 테이블, DB 함수를 기록자, TypeScript를 소비자로 나누자 모기는 같은 구조를 자기 말로 재진술하고 `consumed_at = NULL`을 미완료로 적용했다. 이후 “실물 이동 완료지만 완료 표기 실패” 예외에서도 재시도 시 이미 private이면 완료로 접는다고 답했다.
3. **C4의 두 회수 분리:** `shade_images` 대표 관계 제거와 public→private Storage 이동을 별도 축으로 나눈 뒤, 숨김 해제된 A와 현재 같은 등급 대표 B 사례에서 B 유지라고 답했다.
4. **C5~C6의 귀속 단위 분리:** “파일마다 사용자 소유자 컬럼”과 “기존 `swatch_media.swatch_id` 대조”를 구분한 뒤, 같은 사용자의 다른 발색 key도 거부한다고 답했다. 이어 공유 객체의 숨김·삭제 수명주기 충돌을 “의도치 않은 사이드이펙트”로 재진술했다.
5. **지속 외부화:** 전날 저장한 raw diff 노트와 중간 체크포인트로 C1의 정확한 중단 지점을 재구성했고, 같은 hunk를 추측으로 재작성하지 않고 이어갔다.

### 반박 증거

반박 증거는 0개가 아니다.

1. **C1은 피로 뒤 세션 경계 문제:** 모기가 이전 세션을 지쳐서 끝냈다고 직접 밝혔고, 저장된 체크포인트는 정확한 다음 질문을 보존했다. 재개 지점 질문을 일반적 기억 실패로 해석할 근거가 없다.
2. **C2는 처음부터 골격 대부분이 맞았음:** Storage 업로드 뒤 `mark_stored` 호출, `swatch_media`의 `stored` 전이, `object_key` 기록, 숨김 재검사를 이미 연결했다. 교정된 것은 위험 창의 정확한 위치와 `object_key` 검사의 의미였다.
3. **C3은 실제 이름 설계의 모호성:** `_queue`가 테이블인지 함수인지 이름만으로 확정할 수 없고, DB 함수·테이블·TypeScript 함수가 한 흐름에 함께 존재한다. 재질문은 실제 입력의 구분 부족으로도 충분히 설명된다.
4. **C4는 `회수`의 중의성:** 자료가 대표 관계 제거와 Storage 파일 이동을 모두 `회수`라고 불렀다. 두 축을 명시하기 전의 혼동은 설명 문구의 참조 충돌을 드러낸다.
5. **C5는 새 보안 발견물:** 임의 key 채택은 보안 전용 패스가 새로 발견한 실제 설계 구멍이고, fix5 경계는 세션 도중 처음 제시됐다. 새 지식 질문을 조건 손실로만 볼 수 없다.
6. **피로 조건:** 모기가 전체 동작으로 넘어갈 때 “지친다옹”을 명시했다. 후반의 축약 표현과 종료 선택을 독립 추론 능력의 증거로 확대하지 않는다.

### 잠정 판정

- **컨텍스트 구성 비용 가설:** 부분 지지. 값의 주인·실행 주체·이벤트 순서를 분리한 뒤 같은 사례 적용이 이어졌다.
- **외부화 효과:** 지지. 저장된 raw diff, 시간선, 테이블/함수 역할표, A/B 발색 예시 각각의 직후에 해당 구조의 재진술 또는 적용 답변이 관찰됐다. 어느 표현 하나의 독립 효과 크기는 미측정이다.
- **일반적 작업기억 저하 가설:** 지지 불충분. 전날 중단 지점은 체크포인트로 회수했고, 실제 설계 중의성과 새 보안 경계를 구분해 후속 사례에 적용했다.
- **질문 횟수를 실패 지표로 쓰는 방식:** 반박됨. 질문은 `회수`의 두 의미, 큐의 실행 주체, 발색 단위 소유 경계를 정확히 분리하게 했다.

## 5. 가장 최근 이전 관찰의 다음 예측과 오늘 사례

가장 최근 관찰인 [`2026-08-17-pr520-raw-diff-mid-session-observation.md`](./2026-08-17-pr520-raw-diff-mid-session-observation.md)는 압축 전 체크포인트라 `다음 세션에서 구분할 예측`을 두지 않았고, 선택한 마이그의 경쟁 조건 해석을 `미관찰`로 남겼다. 따라서 가장 최근의 명시적 예측은 [`2026-08-17-representative-photo-policy-session-end-analysis.md`](./2026-08-17-representative-photo-policy-session-end-analysis.md)의 비교 예측을 사용한다.

|---|---|---|
| 익숙한 제품 정책과 낯선 DB 규칙에서 암묵 슬롯 수를 비슷하게 맞춘 짧은 새 사례를 하나씩 사용하면 질문 유형이 슬롯 수보다 도메인 지식에 더 잘 따라가는지 구분할 수 있음 | **미관찰** | 오늘은 실제 PR 흐름을 이어갔고, 제품 정책 사례와 DB 규칙 사례의 슬롯 수를 사전에 맞추지 않았다. 도메인별 질문 유형 차이를 비교하도록 설계하지 않았으므로 이전 예측은 아직 판정할 수 없다. |

별도 체크포인트의 미관찰 항목은 오늘 다음처럼 갱신됐다.

- 선택한 마이그의 경쟁 조건 해석: 같은 사례 안에서 관찰됨.
- 새 이름·값을 넣은 별도 경쟁 조건 전이: 미관찰.
- `object_key` 공유의 새 A/B 발색 사례 적용: 관찰됨. 다만 이는 경쟁 조건과 다른 보안·수명주기 사례다.

## 7. 짧은 종료 기록

- **처음 막힌 지점:** 전날 중단한 raw diff의 재개 위치, Storage 업로드·사용자 숨김·`mark_stored`의 정확한 시간 순서, `swatch_media_lifecycle_queue`의 객체 종류.
- **설명·외부화 뒤 달라진 점:** 시간선을 따라 기존 트리거가 `object_key = NULL`인 행을 놓친 이유를 설명했고, 큐 테이블과 TypeScript 소비자를 구분했으며, 대표 관계 회수와 Storage 회수를 분리한 뒤 숨김 해제 동급 사례에서 B 유지를 적용했다. fix5에서는 다른 `swatch_id`의 key 재채택을 거부하고 공유 객체의 수명주기 부작용을 설명했다.
- **아직 모르거나 다음에 확인할 점:** fix5 구현·검증 결과와 보안 패스의 나머지 발견물은 마스터 작업 진행 중이라 이번 과외에서 다루지 않았다. 경쟁 조건의 새 사례 전이, 시간 지연 뒤 유지, 제품 정책과 DB 규칙의 슬롯 수를 맞춘 비교는 미관찰이다.
