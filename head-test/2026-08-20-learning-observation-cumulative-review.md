흐름은 다음처럼 바뀌었다.

## 3. 세 축별 변화와 근거

### 3.1 설명 입력의 품질

**변화:** 실제 diff보다 설명이 더 어려워지는 방식에서 벗어나, 변경 핵심과 실제 행·이벤트를 먼저 맞추는 쪽으로 좋아졌다.

**효용이 관찰된 방식:**

- 같은 명사를 여러 대상에 쓰지 않고 `swatches` 발색 행, `swatch_media` 사진 사본 행, `shade_images` 대표 관계 행처럼 대상을 분리함.
- 등록·숨김·복사 완료·대표 회수처럼 이벤트 전후를 시간순으로 그림.
- SQL 픽스처의 `IF ... RAISE EXCEPTION`을 성공 조건이 아니라 실패 조건이라고 먼저 고정함.
- URL, `object_key`, Storage bucket, DB 사본 행을 모두 “사진”이라고 부르지 않고 저장 단위를 나눔.
- raw diff와 변경 핵심 한 문장을 먼저 접촉하고, 설명은 그 뒤에 붙임.

**근거:**

- 8월 14일에는 `USING(true)`와 새 숨김 정책, URL 사본과 FK 포인터, DB와 Storage의 트랜잭션 경계를 분리한 뒤 상태 전이가 이어졌다.
- 8월 17일에는 새 사진 등록과 현재 대표 회수, `내 화장품`과 `내 발색샷` 화면 층을 분리한 뒤 제품 판단이 구체화됐다.
- 8월 18일에는 업로드·숨김·`mark_stored` 시간선과 큐 테이블·TypeScript 소비자를 나눈 뒤 같은 구조를 재진술했다.
- 8월 19일에는 공통 마감의 새 숫자 `6초`를 계산했고, 사본 삭제에서 대표 정리로 이어지는 인과 방향을 교정했다.
- 8월 20일에는 변수와 SQL 실패 조건을 먼저 설명한 뒤 `v_mapped=1`, `v_unresolved=1`을 새 조합에 적용하고 변경 전 픽스처 상태를 읽었다.

**남은 한계:** 어떤 표현 하나의 독립 효과를 통제 비교하지 않았다. 설명 뒤 이해가 이어졌다는 관찰은 가능하지만 표·시간선·워크북 중 무엇이 얼마만큼 원인이었는지는 말할 수 없다.

### 3.2 모기의 자기조절

**변화:** 제공된 설명을 수동적으로 받는 수준보다, 컨디션과 재료에 맞는 보조물을 직접 고르고 범위를 조절하는 행동이 뚜렷해졌다.

**근거:**

- 전날 중단한 raw diff의 정확한 위치를 체크포인트와 노트로 회수했다.
- 긴 설명을 `code-diff-notes/temp/`의 한 줄 체크 워크북으로 바꿔 달라고 직접 요청하고, 체크와 모기 메모를 사용했다.
- 공통 마감 코드를 직접 보고 싶다고 요청해 raw diff note로 외부화했다.
- 피로를 명시한 뒤 마지막 적용 질문이나 남은 리뷰 범위를 중단했다. 종료 기록은 이를 실패로 세지 않았다.
- 질문을 통해 X CDN 직접 참조, Storage 직접 SQL 삭제, self-thread 사진 중복, slug 중복 참조, 미사용 ROI 테이블 같은 실제 설계·입력 문제를 분리했다.

이것은 시스템 의존의 양을 재는 자료가 아니다. 다만 현재 기록에서는 설명을 검증 없이 받아들이거나 제품 판단을 전부 넘긴 모습보다, 원문 전제를 의심하고 제품 손해를 직접 선택한 사례가 더 많이 관찰됐다.

### 3.3 새 사례 적용

**변화:** 일부 새 값·새 조합 적용이 자연 과외 안에서 관찰되기 시작했다. 아직 통제된 전이율이나 장기 유지로 해석하지 않는다.

**관찰된 사례:**

- 공통 마감의 새 숫자에서 남은 시간 `6초`를 계산함.
- 새 `v_mapped/v_unresolved` 조합에서 각각 `1`을 적용함.
- 같은 `object_key`를 다른 `swatch_id`가 채택하는 사례에서 거부와 수명주기 충돌을 연결함.
- 숨김 해제된 사진과 현재 동급 대표가 함께 있는 사례에서 현재 대표 유지를 적용함.
- 다중-shade 사진의 단독샷 손실과 오매핑 손해를 비교해 오매핑 방지를 우선하는 정책을 선택함.

**한계:** 도메인 학습, 설명 품질 개선, 반복 노출이 함께 누적됐다. 이를 일반적 기억력이나 인지능력 향상으로 분리할 수 없다. 피로 뒤 답하지 않은 마지막 사례는 그대로 `미관찰`이다.

## 4. 기존 미관찰 항목 정리

`미관찰`은 갚아야 할 빚이 아니라 당시 자료로 결론 내리지 않았다는 경계다. 다음 문서로 자동 승계하지 않는다.

| 기존 항목 | 분류 | 이유 |
|---|---|---|
| 새 이름·값을 넣은 사례 적용 | 종료 | `6초`, `v_mapped/v_unresolved`, 다른 발색의 같은 key 사례가 자연 과외에서 관찰됐다. 별도 시험이 과외 방식을 더 바꾸지 않음 |
| 경쟁 조건의 별도 새 사례 전이 | 자연 관찰 | 관련 PR을 실제로 공부할 때 자연스럽게 나오면 기록하면 충분함 |
| 시간 지연 뒤 보조물 없는 유지 | 종료 | 카드·노트로 기억을 외부화하는 실제 작업 방식과 맞지 않고, 결과가 설명 방식을 유용하게 바꾸지 않음 |
| 제품 정책과 DB 규칙의 난도·슬롯 수 맞춤 비교 | 종료 | 순수 연구 질문에 가깝고 평소 과외를 시험으로 바꿀 위험이 큼 |
| 기계식 A/B·타이머 실험 | 종료 | 모기가 별도 실험을 명시적으로 다시 원할 때만 선택 도구로 사용함 |
| 실제 화면에서 공용 대표가 개인 공간을 침범하는 느낌 | 자연 관찰 | 제품 UAT에서 실제로 다시 나타날 때 판단할 항목이며 머가리 검증 과제가 아님 |

현재 별도로 시험해서 해소해야 할 `확인 필요` 항목은 없다.

## 5. 다음 세션에서 실제로 바꿀 것

1. **원문 접촉 뒤 설명한다.** PR 본문을 일단 완독하고 실제 변경 파일·핵심 diff를 본 뒤, 모기가 이해한 핵심 한 문장을 먼저 만들 수 있게 둔다. 그다음 과외냥이 설명과 다른 부분만 원문으로 돌아가 확인한다. 첫 완독에서 전부 기억하거나 이해하게 만들지 않는다.
2. **설명의 대상을 먼저 고정한다.** 설명을 시작할 때 필요한 범위에서 `어느 테이블·행·컬럼인지 → 값의 주인이 누구인지 → 어떤 이벤트인지 → 변경 전후 값이 무엇인지`를 먼저 밝힌다. 모기가 피곤하면 지도·표·한 줄 워크북을 바로 쓰고, 힘이 있으면 원문과 diff를 먼저 본 뒤 작은 재진술 한 번만 한다.

과거 가설로 모기가 막힐 곳을 예단하거나, 이 문서의 미관찰 항목을 해소하려고 질문을 삽입하지 않는다. 다음 누적 검토 전까지는 위 두 변화와 이미 효용이 관찰된 외부화만 인수인계로 사용한다.
