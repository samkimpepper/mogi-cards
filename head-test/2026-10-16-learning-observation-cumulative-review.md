## 2. 이번 구간의 결론

**사용자 사건 → 구체 상태 변화 → 필요한 구현 근거** 순서는 이번 구간에서도 효용이
관찰됐다. 다만 한 대목을 이해했다고 한 반응과 세션 전체에 대한 만족은 별개로 보존해야
한다. 특히 todo-ops PR #1 설명의 전체 사용감은 모기의 사후 평가상 불만족이었다.

구간 A에서는 일괄 등록, 사진 삭제, 검색 결과처럼 사용자 사건을 먼저 잡고 값의 주인과
행·컬럼·분기를 펼쳤을 때 긍정적인 사용감과 후속 연결이 기록됐다. 인터뷰에서는 실제
발화·행동과 해석을 나누는 교정이 적용됐지만, 직접 작성 부담과 피로도 함께 명시됐다.

구간 B에서도 PR #539의 행·상태표와 PR #546의 두 결과 전달 경로 비교 뒤 연결이
관찰됐고, PR #33에는 이해하기 쉬웠다는 평가가 있었다. 반면 todo-ops PR #1에서는
시험 사례 하나의 다이어그램 뒤 이해했다는 반응이 있었어도, 셸 명령·조회 프로세스·실행
예정 폴더의 시점을 따라가는 부담과 설명 전체에 대한 불만족이 남았다.

셸에 익숙하지 않은 점은 모기가 직접 밝힌 조건이다. 설명에서 실제 실행 위치와 변수에
적힌 실행 예정 위치를 같은 「현재 폴더」라는 말로 부른 문제도 기록에 있다. PR 방향이
맞지 않았을 가능성은 모기가 제시한 가능성이다. 이 셋의 상대적인 영향이나 단일 원인은
현재 자료로 분리할 수 없다. 설명만 바꾸면 해결된다거나 PR 방향이 나빴다고 확정하지
않는다. 모기의 「그외는 괜찮았다」는 평가도 모든 기술 세부의 이해 완료로 넓히지 않는다.

**이어갈 방식:** 같은 사건의 질문을 먼저 묶기, 구체 값 하나와 행·컬럼 전후를 따라가기,
서로 다른 경로를 같은 기준의 표나 짧은 그림으로 비교하기다. raw diff를 실제 근거로
확인하되, 학습자가 raw diff만으로 의미를 먼저 알아내게 하지 않는다. PR #539는
상태표가 이해를 도운 사례이며 raw diff 우선 설명을 의무화할 근거가 아니다.

**입력 문제로 남길 것:** PR #546의 `step`·`resendIn`, todo-ops의 실제 프로세스 실행
폴더·변수에 저장한 실행 예정 폴더처럼 비슷하게 표현된 서로 다른 대상을 구분한다.
특히 가드가 명령 실행 전에 검사하는데 `cd`가 이미 실행된 듯 설명하면 시점이 달라진다.
필요한 코드에는 소속 파일·호출자·호출 시점과 해당 줄이 실행문인지 주변 문맥인지도
가까이 붙인다. 이는 설명의 수정 대상이지 모기의 능력에 대한 근거가 아니다.

todo-ops의 시험 문답에서는 「검증하려는 조건이 실제 입력에 만들어졌는가」와
「원하는 이유로 실패했는가」가 구분됐다. 정상 가드와 분기를 끈 가드가 다른 이유로
같은 종료 코드를 낼 수 있었다. 향후 시험을 설명할 때는 기존 가이드대로 입력·관찰
결과·앱에서 남은 확인 범위를 먼저 보여주며, 작성자 보고와 직접 재실행을 구분한다.
이 제품 시험 발견을 개인 학습 측정이나 모든 시험의 단일 필수 기법으로 바꾸지 않는다.

### 3.2 모기의 자기조절

구간 A에서는 인터뷰의 유도 질문을 스스로 멈추고, 실제 발화와 해석을 나누는 기록을
직접 작성했다. PR #534는 중요도에 맞춰 간단한 설명을 요청했고, PR #535에서는 개인
공부와 제품 설계 이해의 범위를 구분했다. PR #536으로 전환할 때는 과열을 알리고
의도적인 프로브를 중단했다. 활성 지침에 구체적인 개인 인지 가설을 반복 노출하지
말라는 경계도 모기가 직접 지적했다.

구간 B에서는 PR #539의 기대 동작과 충돌 조건을 직접 정의하고 작업 빈도에 맞춰
정책을 단순화했다. PR #33에서는 명령 이름과 실패 분리 시험을 먼저 물었고, todo-ops
PR #1에서는 일반 설명과 구체 사건의 이해를 구분해 다이어그램을 요청했다. 시험에 관한
제안의 의도가 한 사례로 좁아지자 일반적인 검증 조건을 말하는 것이라고 바로잡았다.
피로 표현의 시점에 대한 과외냥이의 해석도 정정했다.

이번 사후 평가는 당시의 부분적인 「이해했다」 이후에도 전체 설명의 불만족을 별도로
알린 사례다. 만족을 추정하지 않고 그 평가를 그대로 인수한다. 필요한 형식·범위·중단을
모기가 고른 사실을 보존하며, 특정 보조물을 매번 쓰게 하는 규칙을 만들지 않는다.

### 3.3 새 사례 적용

두 구간 모두 이름이나 값을 바꾼 별도의 새 사례 적용은 시행하지 않아 **미관찰**이다.
PR #535의 업무 모델 연결, PR #539의 충돌 조건 발견, todo-ops 시험 기준의 일반화
요청은 각각 기록된 연결로 보존한다. 이를 별도 사례에서 검증된 전이 성공으로 세지
않으며, 미관찰을 해소하려는 과제도 만들지 않는다.

## 5. 다음 세션에서 실제로 바꿀 것

1. **사용자 사건 다음에, 혼동되는 대상과 시점을 먼저 펼친다.** 기존의 사용자 행동 →
   화면·저장 상태 변화 순서를 유지한다. 여러 프로세스·화면 이동·실행 전 검사가 얽히면
   구체 값 하나로 `시점 / 동작 주체 / 실제 위치·대상 / 변수에 기록한 값 / 실행 여부` 중
   필요한 열만 둔 짧은 표나 그림을 먼저 보여준다. 실제 실행 위치와 실행 예정 위치를
   같은 「현재」라는 말로 묶지 않는다. 이 외부화 뒤 필요한 코드 몇 줄을 파일·호출
   맥락과 함께 연결하며, 셸 문법은 그 사건을 읽는 데 필요한 만큼 가까이 설명한다.
2. **부분 이해 반응으로 설명 전체를 성공 처리하지 않는다.** 특정 표·그림 뒤의 연결은
   해당 대목의 관찰로만 남긴다. 모기가 궁합이 안 맞거나 불만족이라고 하면 그 평가를
   그대로 보존하고, 설명 입력의 문제·아직 낯선 개념·제품 계약이나 PR 방향의 문제 중
   확인한 사실과 미분리 원인을 나눈다. 같은 설명을 더 길게 반복하거나 이해 확인을
