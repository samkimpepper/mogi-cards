## 짧은 기록

- **처음 막힌 지점:** PR #4에서 3-way merge, 원본 적용·경로 치환의 순서, 세 파일의 역할을 물었다. 코드 세 줄을 본 뒤 `$OPS`를 main 브랜치로 읽고 `-C`·`grep -qx`와 검사 대상이 무엇인지 물었다. A/B 리뷰는 개수만으로 차이를 모르겠고 jargon 때문에 이해되지 않는다고 했다. PR #6에서는 병합 커밋의 두 부모와 main·원본·작업 브랜치의 시점별 상태를 요청했다. PR #36에서는 수정 시각 없음과 -1700의 관계, 원인 없는 오류와 전역 핸들러, 안전 규칙과 원문 출력 제한을 물었다.
- **설명 추가 없이 바로 연결한 지점:** 앞선 설명 뒤 모기는 추가 설명 없이 훅과 테스트가 상호 보완한다고 재진술했다. PR #6의 가상 `retry_limit` 사례 뒤에는 main의 값이 우리 추가 변경인지 받아온 원본 변경인지 구분하려는 것인지 물었다. PR #36의 값 없음 설명을 Java의 null 처리 누락에 연결하고, 오류 출력을 Spring의 예외 메시지·스택트레이스와 비교했다. 모두 해당 설명 뒤의 연결이며 설명 전 독립 해결이나 모든 세부 이해로 세지 않는다.
- **설명·외부화 뒤 달라진 점:** 첫 답변을 한 턴에 모두 쏟자 모기는 내용은 좋지만 순서를 구성해 2~3턴으로 나눠달라고 요청했다. 이후 A/B는 금지된 push를 심은 구체 사건 하나로 풀자 이해했다고 말했다. Git 설명에서는 커밋과 브랜치 이름을 나누고 `시점 / 방금 한 행동 / main / upstream-template / 작업 브랜치` 표를 제시하자, 모기는 그 표까지만 보고 이해했다고 명시했다. 표 뒤 설명 전체를 읽었다고 기록하지 않는다. 이어 부모 커밋 저장을 재진술하고, 다음 업데이트의 비교 기준과 Squash의 차이를 설명한 뒤 원본 변경·우리 변경의 구분으로 연결했다. Things 오류 설명에서는 값 없음 자체와 날짜 계산 오류를 구분한 뒤 null 처리로 연결했고, 원본 메시지 대신 고정 원인 분류를 남긴다는 보충 뒤 해당 PR을 마무리했다.
- **아직 미관찰이거나 다음에 확인할 점:** 별도의 새 사례 적용은 하지 않았다. 설명용 `retry_limit` 가상 사례는 함께 풀이한 설명이지 독립 적용 시험이 아니다. Git을 직접 조작하거나 낯선 이력에서 같은 규칙을 적용하는 과정, A/B의 나머지 결함·문법 취약성 전체 독해, PR #6의 새 dispatch-smoke 실제 동작은 미관찰이다. PR #36의 원인 분류·스택트레이스 보충 뒤 독립 재진술도 미관찰이다. 현 스크래치패드의 질문 3개는 답했으며 미답 질문은 없다. 이 미관찰 범위를 자동 재개 과제로 만들지 않는다. PR #4 관련 두 메시지(`msg_27faa0778c4f`, `msg_13e64053aa97`)는 전송 접수만 직접 확인했고 수신·구현 완료로 기록하지 않는다. 테스트 요청 파일럿은 문서만 만들었으며 적용 횟수는 0이다.
