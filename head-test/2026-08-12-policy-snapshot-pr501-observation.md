## 판정

**외부화 효과는 판정 불가.** 문단 조건과 표 조건을 모두 시도했지만, 문제의 난도를 동급으로 통제하지 못했고 설명과 즉시 피드백이 누적됐다. 표 자체와 질문에도 입력 결함이 있었으며, 지연 재검사 전에 모기가 피로를 명시해 중단했다.

따라서 이번 기록은 지능이나 전반적 추론능력의 판정이 아니다. 외부화가 도움이 된 듯한 관찰, 처음 접한 PostgreSQL·GitHub 지식의 영향, 설명 입력의 결함, 피로를 서로 분리해 다음 세션의 예측으로만 남긴다.

## A. 문단 조건 관찰

긴 문단으로 정책 스냅샷의 생성·비교 구조, 사람말 요약의 범위, 1라운드 누락을 설명했다. 최초 출력은 줄바꿈이 없는 한 덩어리여서 모기가 즉시 가독성 문제를 지적했고, 같은 내용을 여러 짧은 문단으로만 다시 제시했다. 표는 아직 제공하지 않았다.

| 질문 종류 | 관찰 |
|---|---|
| 사실 회상 | 커밋된 스냅샷과 CI가 PR의 로컬 DB에서 재생성한 스냅샷을 비교한다고 답했다. CI가 왜 독립 재생성해야 하는지는 처음에 이해하지 못했다고 명시했다. 설명 뒤 “문서가 항상 최신 사본인지 검사한다”로 재진술했다. |
| 상태 추적 | 마이그레이션은 그대로인데 스냅샷만 손으로 고치면 커밋본과 CI 재생성본이 불일치해 빨간불이라고 답했다. |
| 새 사례 추론 | 생성기가 관측하지 않는 RLS 활성 상태가 바뀌면 두 스냅샷이 일치할 수 있다는 사례에서, 초록불의 원래 범위가 비교 일치뿐이라고 반문했다. |
| 모순 탐지 | 과외냥이가 “초록불이 증명하던 무엇이 깨지는가”라고 물으며 보안 구조 전체의 안전을 암묵적으로 섞자, 초록불은 최신 DB 상태에서 생성한 스냅샷 비교만 증명하며 전체 보안 안전은 애초 목적이 아니라고 지적했다. |

모순 탐지 응답은 중요한 관찰이다. 모기가 조건을 잃은 것이 아니라, 설명자가 넓혀버린 **비교 일치·관측 범위·전체 안전**의 경계를 스스로 다시 좁혔다.

## B. 외부화 조건 관찰

처음에는 `pg_class`, `pg_policies`, 권한 정보를 한 표에 넣었지만 첫 열을 모두 “테이블”이라고 불러 정보 출처의 종류와 값의 주인을 섞었다. 모기가 세 출처의 차이를 모르겠다고 질문했고, 다음처럼 표를 고쳤다.

| 정보 출처 | 값의 주인 | 관측하는 것 |
|---|---|---|
| `pg_class` | 대상 테이블 | 테이블 전체의 RLS 작동 상태 |
| `pg_policies` | 개별 RLS 정책 | 정책의 대상 명령·역할·조건·PERMISSIVE/RESTRICTIVE 성격 |
| 권한 정보 | 권한을 받은 역할 | 테이블 명령을 시도할 자격 |

수정한 외부화를 계속 보인 뒤 다음을 적용했다.

- 정책이 남아 있고 테이블의 RLS만 꺼지면 변화는 `pg_class`에 나타난다고 답했다.
- RLS는 켜진 채 정책이 PERMISSIVE에서 RESTRICTIVE로 바뀌면 `pg_policies` 변화라고 답했고, 실제 접근이 제한될 것 같지만 단정할 수 없다고 경계를 붙였다.
- `PUBLIC`의 SELECT 권한 회수 사례에서는 정보 출처를 권한 정보로 맞췄지만, 전후 값을 `없음 → 있음`으로 한 번 뒤집었다. 정확한 전이는 `있음 → 없음`이다.
- 세 출처가 모두 “참”이어야 조회 가능한지 스스로 필요충분조건을 질문했다. `GRANT`는 명령 자격이고 RLS는 결과 행을 고르는 별도 관문이라는 흐름을 제시하자, 적용 가능한 PERMISSIVE SELECT 정책이 없으면 행이 보이지 않는다고 답했다.
- RLS에서 막힐 때 권한 오류 대신 `0 rows`를 본 과거 경험을 스스로 떠올려, “어느 행을 보여줄 것인가”라는 설명과 연결했다.
- 정책 추가만 보고 “실제 조회 가능”이라고 쓰면 안 되는 이유를 PostgreSQL의 두 관문으로 설명했다.
- 생성기를 다시 실행해도 DB 실측과 다른 RLS 상태를 쓰는 사례를 생성기 스크립트 오류라고 답했다.

## 입력 결함과 새 지식 부족

아래는 모기의 오류로 채점하지 않는다.

1. 문단 조건을 한 줄짜리 거대 문단으로 출력해 가독성을 불필요하게 낮췄다.
2. “초록불이 증명하던 무엇이 깨지는가”라는 질문이 비교 일치와 전체 보안 안전을 섞었다. 모기가 이 전제를 바로잡았다.
3. 최초 외부화 표가 시스템 목록·시스템 뷰·권한 정보를 같은 종류의 “테이블”처럼 묶었다. `pg_class`와 `pg_policies`의 차이에 대한 질문은 이 표의 입력 결함과 처음 접한 PostgreSQL 카탈로그 지식으로 설명된다.
4. 실제 DB와 커밋된 스냅샷이 다를 때 원인을 마이그레이션과 생성기 중 하나로만 고르게 한 질문은 “생성기를 실행하지 않음”이라는 절차상 원인을 누락했다. 모기가 이 가능성을 먼저 제시했다.
5. DB 무관 PR의 필수 체크 동작 질문에, 경로 필터로 워크플로가 생략되면 GitHub가 요구된 성공 결론을 받지 못해 머지를 막는다는 제품 고유 규칙을 먼저 제공하지 않았다. 모기는 기존 `paths` 지식에 따라 “무관하면 실행하지 않는다”고 답했고, 질문 의도를 이해하지 못했다고 표시했다. 이는 조건 유지 실패가 아니라 새 지식 부재다.

## 피로와 중단

필수 체크의 빠른 성공 분기를 설명한 뒤 같은 상황을 다시 물었을 때 모기가 “더 이상 머가리가 안 돌아간다”고 명시했다. 이 시점에 질문을 중단했다.

피로가 명시된 뒤의 무응답은 추론 실패로 기록하지 않는다. 지연 후·요약 없음과 지연 후·표 있음 조건은 시행하지 못한 것으로 본다.

점수 척도와 동급 난도를 사전에 고정하지 않았으므로 정답 수를 수치화하지 않는다.

## 세션 종료 기록

- 외부화 효과: **판정 불가** — 표 수정 뒤 적용은 좋아졌으나 난도 통제·지연 검사가 없고 설명 학습이 섞임
- 가장 자주 난 오류: 반복 패턴 없음. 관측된 오류는 권한 회수 전후 값 반전 1회
- 모기가 스스로 발견한 입력 결함·모순: 초록불의 범위를 전체 안전으로 넓힌 질문, 생성기 미실행 가능성을 누락한 선택 범위, 필수 체크 질문의 의도 불명확성
- 설명 직후 수정 여부: 관찰된 새 개념은 바로 재적용함
- 지연 후 유지 여부: 미측정
- 코드베이스 비숙련이나 문서 품질로 설명되는 부분: PostgreSQL 카탈로그 구조, PERMISSIVE/RESTRICTIVE 조합, GitHub 필수 체크와 경로 필터의 상호작용, 최초 표 설계
- 피로 영향: 명시됨. 필수 체크 재질문부터 판정 자료에서 제외
- 다음 세션에서 다시 확인할 예측: 충분히 쉰 상태에서 출처·주인·이벤트·전후 값이 정확히 분리된 외부화를 먼저 설계하면, 문단 조건보다 상태 추적과 새 사례 적용이 안정적으로 좋아지는가

최소 두 번의 서로 다른 새 카드에서 같은 패턴이 반복되기 전에는 잠정 결론을 갱신하지 않는다.
