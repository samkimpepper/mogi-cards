# 실패상황 테스트 요청 — 잘못된 사용과 고장 난 도구 나누기

작성일: 2026-10-19

모기가 다음에 에이전트에게 테스트를 부탁할 때 복사해서 쓰는 **임시 프롬프트 파일럿**이다. 두 종류를 나눠 요청하면 필요한 시험이 덜 빠지는지 다음 요청 3건에서 살펴본다. 이번 문서 작성은 실행 1회로 세지 않는다.

## 기억할 표

| 구분 | 예 |
|---|---|
| **잘못된 사용 상황을 만들기** | main에서 병합하려 하거나, 잘못된 설정값을 주면 안전하게 거부하는가 |
| **도구를 일부러 고장 내기** | main 차단 코드를 지우거나 금지된 push를 추가하면, 테스트가 그 잘못을 잡는가 |

첫째는 정상 도구에 잘못된 입력·사용 상황을 주는 시험이다. 적절히 거부하고 보호할 상태를 유지하면 **테스트 통과**다. 둘째는 임시 복사본의 도구를 일부러 잘못 바꾼 뒤 같은 테스트를 실행하는 검증이다. 심은 잘못을 잡아서 **테스트가 실패해야** 탐지 근거가 된다.

## 복사해서 쓸 프롬프트

```text
이번 기능이 해야 하는 일과 하면 안 되는 일을 먼저 짧게 정리하고,
정상 기능 시험을 유지하면서 아래 두 종류를 나눠 검증해줘.

1. 잘못된 입력·사용 상황
   검증하려는 상황을 시험에서 직접 만들어줘.
   원하는 이유로 거부되는지와, 바뀌면 안 되는 상태가 유지되는지 확인해줘.
   다른 오류 때문에 우연히 실패한 것을 성공으로 세지 말아줘.

2. 도구 자체의 잘못
   중요한 약속을 어기는 변경을 임시 복사본에 하나씩 넣고,
   같은 테스트가 그 잘못을 잡아서 실패하는지 확인해줘.
   원래 도구에서는 통과하고 고장 난 복사본에서는 실패하는지 비교해줘.

어떤 약속을 어떤 입력·고장으로 확인했고, 무엇을 관찰했는지 보고해줘.
실행하지 않은 범위와 테스트가 놓친 잘못도 밝혀줘.
실제 운영 데이터·원격 저장소에 피해를 주는 동작은 하지 말고 가짜 환경을 써줘.
```

기능별로 main·설정·push 대신 해당 입력, 변경하면 안 되는 데이터, 금지된 행동을 넣는다. 모든 기능에 같은 오류 메시지 검사나 모든 종류의 고장 시험을 강제하지 않고, 중요한 약속과 확인 비용에 맞춰 범위를 정한다.

## 훅·정상 기능 시험과의 관계

- 훅 등 실행 중 차단 장치는 실제 잘못된 행동을 막는다. 테스트는 그 장치가 정상 동작하고, 잘못 수정되면 이를 발견하는지 확인한다.
- 친구 변경 반영·우리 설정 보존 같은 정상 기능 시험도 계속 필요하다. 실패상황 시험만 늘려 정상 동작 검증을 대체하지 않는다.
- 매번 테스트 두 벌을 새로 만들어 A/B 비교할 필요는 없다. 이 파일럿은 요청을 두 종류로 나누는 방식이며, 기존 시험을 보강하고 실행해도 된다.
- 통과 개수만으로 시험의 우열을 정하지 않는다. 무엇을 잡고 놓쳤는지 본다.

## 적용·중단·사후 판단

- 모기가 이 프롬프트를 써보려는 실제 테스트 요청에만 적용한다. 세션마다 자동 실행하거나 학습 과제를 만들지 않는다.
- 다음 요청 3건을 살펴본 뒤 자동 적용을 멈추고, 모기와 유지·수정·폐기를 정한다. 3건 전에도 모기가 원하면 중단한다.
- 부하가 과하거나 검증 대상과 맞지 않으면 범위를 줄이거나 해당 요청에서는 생략한다. 실제 운영 저장소를 고장 내지 않는다.
- 실행 수를 채워도 영구 규칙으로 자동 승격하지 않는다. 새 프롬프트가 더 나았는지, A의 누락 원인이 모기의 입력이었는지는 미리 확정하지 않는다.
