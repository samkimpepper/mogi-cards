# 커밋 메시지와 변경 전후 그림으로 순서 따라보기

여러 커밋에 걸쳐 바뀌는 PR에서, 커밋 메시지 옆에 코드의 관계·값이 어떻게 달라졌는지
짧은 그림을 붙여 순서대로 본다. **첫 시험은 조건에 맞는 PR 한 건**으로 좁게 잡는다.
모든 PR의 기본 설명 절차로 만들지 않는다.

## 적용할 때

- `status: pilot`이고 `completed_cases < planned_cases`인 동안만 적용한다.
- 과외에서 자연스럽게 다루는 PR 중, 의미 있는 변경이 여러 커밋에 나뉘어 있어
  전후 관계를 차례로 보면 흐름을 이해하는 데 도움이 될 만한 경우에 시도한다.
  커밋 수만 많거나 문구 수정만 반복되는 경우에는 억지로 장면을 만들지 않는다.
- 이미 승인된 이 한시 시험의 조건이 맞으면 과외냥이가 첫 설명을 준비한다.
  모기에게 매번 설명 형식을 다시 고르게 하거나 구현·머지 판단을 요구하지 않는다.
- 모기의 즉답 요청과 자유 문답이 우선이다. 원하지 않거나 번거로우면 바로 생략·중단한다.

## 보여줄 것

1. PR의 base·판독 HEAD와 선택한 커밋 SHA·부모 SHA를 확인한다. 커밋 메시지와
   해당 diff·필요한 주변 코드를 읽어 그림의 근거를 잡는다.
2. 처음에 사용자에게 생기는 변화나 이번 구조 정리의 목적을 짧게 설명한다.
3. 핵심 커밋 몇 개를 고르고, 각 장면에 **커밋 링크·메시지 → 변경 전/후 그림 →
   필요할 때 원본 코드 몇 줄**을 붙인다. 모든 커밋에 그림을 만들지는 않는다.
4. 그림은 터미널에서도 읽히는 글자 그림을 기본으로 한다. Mermaid 렌더링을 요구하지 않는다.
   파일 이동은 상자의 이동, 의존성 변경은 연결 전후, 중복 제거는 흐름의 통합,
   결과 형식 변경은 구체적인 입력·출력 값처럼 해당 변경에 맞는 표현을 고른다.
5. 화살표가 import인지 호출인지 값 전달인지 가까이에 밝힌다. 단순화한 그림과
   실제 원문을 구분하고, 한 장면의 대상·시점이 대응하도록 한다.

커밋에 남은 변경 순서는 실제 파일 열람·검색·편집 순서와 같다고 가정하지 않는다.
실제 작업 기록을 읽지 않았다면 읽기·편집·실패 장면이나 당시 의도를 재구성하지 않는다.
실패·방향 전환이 없어도 파일 관계나 구축 순서가 드러나는 변경을 다룰 수 있다.

## 남길 관찰과 끝내는 조건

- 한 PR의 그림 여러 장과 후속 질문을 **한 건**으로 센다.
- 실제 설명 뒤 PR·판독 SHA·선택한 커밋·보여준 그림의 종류와 근거를 남긴다.
  모기가 표현한 도움·부담·더 보고 싶은 범위를 보존하고, 반응이 없으면 `미관찰`로 쓴다.
- 커밋 메시지 읽기, 그림의 사용감, 실제 코드 독해, 새 사례 적용은 구분한다.
  그림이 좋다는 반응만으로 코드 이해·기억·전이가 확인됐다고 기록하지 않는다.
- PR 한 건의 설명을 실제로 수행한 뒤 기존 `scripts/pilots.py record`로 기록한다.
  1/1이 되면 `awaiting-review`로 두고 자동 적용을 멈춘다. 모기와 유지·수정·폐기를 정한다.
  조건에 맞지 않거나 못 했으면 횟수를 올리지 않는다.
- 별도 노트를 만드는 것은 필수가 아니다. 다시 볼 자료를 요청받으면 기존 공책 규칙을 따른다.
