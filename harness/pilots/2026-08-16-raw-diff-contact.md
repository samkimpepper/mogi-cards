# 계획 — PR 과외에서 실제 raw diff 먼저 접촉하기

상태: **임시 파일럿**. 다음 PR 과외 2~3회에서 써보고 유지·수정·폐기를 결정한다. 이 문서는 제품 구현이나 머지 판단의 SSOT가 아니라, 모기 과외 UI를 조율하기 위한 개인 공책이다.

## 한 줄 목적

GitHub 화면에서 관련 줄을 찾아다니는 마찰은 과외냥이가 줄이되, 모기가 **실제 변경 원문을 자기 눈으로 보는 단계**는 설명이나 카드로 대체하지 않는다.

## 해결하려는 문제

- 모기는 PR 카드와 설명은 읽어도 실제 code diff는 뒤로 미루기 쉽다.
- 특히 코드리뷰 뒤 fix에서는 리뷰 지적과 실제 수정 줄을 직접 연결해볼 때 이해가 잘 이어졌다.
- 핵심 hunk만 선별하면 의도한 변경은 이해하기 쉽지만, 전체 diff를 훑다가 예상 밖의 이상한 변경을 발견할 기회가 줄어든다.
- 현재 시작 화면에서 PR 카드와 code diff note가 서로 다른 선택지이므로, PR 카드를 고르면 코드 접촉이 별도 과제로 밀릴 수 있다.

## 경계

- 이 파일럿은 **대상 PR이나 실제 fix diff가 있는 과외**에만 적용한다. 착수 전 설계·SPEC처럼 아직 diff가 없는 카드에는 적용하지 않는다.
- 과외냥이는 제품 저장소를 읽기만 한다. diff를 보다가 발견한 문제는 제품에서 직접 고치지 않고 프리앰블의 마스터 전달 경로를 따른다.
- raw diff 접촉은 Review Gate Quiz, 지능 검사, 머지 승인 게이트가 아니다.
- diff를 보지 못했거나 샛길에서 이상을 발견하지 못한 결과는 실패가 아니라 `미관찰` 또는 `발견 없음`이다.
- 기존 문서의 `reviewed`는 모기만 바꾼다. `merge_ready`는 `pr-cards/` 문서에서만 쓴다.

## 한 세션의 기본 흐름

```text
PR이 주장하는 의도
→ 전체 변경 지도
→ 핵심길: 주요 구현 또는 review fix의 raw diff
→ 연결된 테스트·검증 raw diff
→ 모기의 첫 관찰
→ 과외냥이 설명
→ 샛길: 모기가 파일 목록에서 하나 선택
→ 안 본 변경 목록
→ 리드카드의 이유·위험·판단 근거
```

### 1. 먼저 판독 범위를 고정한다

과외냥이는 diff를 보여주기 전에 아래를 적는다.

- 대상 PR 번호
- 전체 PR을 보는 경우: base와 판독한 HEAD SHA
- 특정 fix를 보는 경우: fix 직전 SHA와 fix 반영 SHA
- 판독 시각 또는 카드에 이미 고정된 판독 시점

PR에 새 fix가 돌았는데 어느 SHA를 보고 있는지 확정하지 못하면, 과외냥이는 기억이나 카드 설명으로 raw diff를 재구성하지 않는다. 판독 범위를 확인할 수 없다고 먼저 말한다.

### 2. 전체 변경 지도를 먼저 보여준다

설명으로 파일을 줄이기 전에 다음을 빠짐없이 보여준다.

- 변경 파일 전체 목록
- 파일별 추가·삭제 규모
- 생성·삭제·이름 변경 여부
- generated·lock·snapshot처럼 사람이 주로 읽지 않는 파일도 목록에는 유지

분량 때문에 hunk를 가져오지 않은 파일은 마지막에도 다시 남긴다.

### 3. 핵심길은 실제 diff 그대로 보여준다

#### 일반 PR

- 주요 동작이 실제로 바뀐 구현 hunk 1개부터 시작한다.
- 상태·DB·권한·외부 인터페이스가 함께 바뀌면 그 경계 hunk를 추가한다.
- 가장 가까운 테스트 또는 구조 검증 hunk를 연결한다.

#### 코드리뷰 뒤 fix

전체 PR의 base diff만 보여주지 말고, 가능하면 **fix 직전 → fix 반영** 비교를 우선한다.

```text
리뷰가 문제라고 주장한 것
→ fix 직전 코드
→ fix가 바꾼 줄
→ 그 fix를 확인하는 테스트·실측
```

리뷰 보고도 하나의 주장이고, fix diff와 검증 결과가 그 주장을 수리했다는 증거임을 구분한다.

#### raw 보존 규칙

- 파일 경로와 hunk header를 붙인다.
- `+`·`-`와 주변 문맥을 포함한 실제 diff를 그대로 인용한다.
- 설명하기 좋게 코드를 다시 쓰거나 최종 코드 조각으로 바꾸지 않는다.
- 길면 hunk 단위로 덜어내되, 한 hunk 내부를 임의로 이어 붙이지 않는다.
- 과외냥이의 “왜 가져왔나”와 해설은 raw diff와 시각적으로 분리한다.

### 4. 설명 전에 모기가 한 번 본다

과외냥이는 raw hunk를 보여준 뒤 가벼운 주관식 질문 하나만 한다.

> 이 줄들에서 실제로 무엇이 달라진 것 같아?

정답 시험이 아니다. 모기가 용어·주어·시점부터 묻고 싶으면 그대로 자유 문답으로 간다. 설명이 먼저 필요하다고 하면 파일럿을 고집하지 않고 설명한다.

### 5. 과외냥이는 관계를 풀어준다

첫 관찰 뒤 설명할 때는 최소한 다음을 명시한다.

- 어느 파일·함수·테이블·행·컬럼인가
- 값이나 동작의 주인은 누구인가
- 어떤 이벤트에서 실행되는가
- 변경 전 값·동작은 무엇인가
- 변경 후 값·동작은 무엇인가
- PR이 주장한 의도와 이 hunk가 어떻게 연결되는가
- 이 hunk만으로는 무엇을 증명하지 못하는가

### 6. 샛길 파일은 모기가 고른다

핵심길 뒤 과외냥이는 아직 직접 보지 않은 파일 목록을 다시 보여준다. 모기가 이름을 보고 끌리거나 이상해 보이는 파일 하나를 고른다.

- 과외냥이가 무작위 hunk를 대신 고르지 않는다.
- 선택된 파일에서는 먼저 raw diff만 보여주고 해석을 선행하지 않는다.
- 모기가 원하는 파일이 없거나 피곤하면 샛길은 생략한다.
- 샛길의 목적은 점수가 아니라, 핵심 설명이 가리지 못한 예상 밖의 변경과 질문을 만날 여지를 남기는 것이다.

## PR 크기와 위험에 따른 양 조절

### 작은 일반 PR

- 전체 파일 지도
- 구현 hunk 1개
- 테스트 hunk 1개
- 원하면 샛길 파일 1개

### review fix가 핵심인 PR

- fix 직전·반영 SHA
- 주요 fix hunk
- 연결 테스트·검증
- 전체 PR에서 아직 안 본 파일 목록
- 원하면 샛길 파일 1개

### DB·권한·데이터 의미·수명주기·동시성처럼 위험한 PR

- 전체 파일 지도
- 앱 동작 hunk
- DB·정책·상태 전이 hunk
- 테스트·검증 hunk
- 마이그레이션의 되돌림·기존 데이터 영향이 있으면 그 근거
- 안 본 파일 목록과 전체 diff 진입 선택

분량은 위험 분류만으로 기계적으로 늘리지 않는다. 실제 PR 크기와 모기의 피로를 함께 본다.

## 과외 화면 임시 형식

```text
PR #NNN — 실제 변경 접촉
판독 범위: <base/fix 직전 SHA>..<HEAD/fix 반영 SHA>

[PR이 주장하는 의도]
<출처를 붙인 한 문장>

[전체 변경 지도]
- path/a.ts  +12/-4
- path/a.test.ts  +20/-2
- migration.sql  +31/-0

[핵심 raw diff]
diff --git ...
@@ ... @@
- ...
+ ...

[모기의 첫 관찰]
이 줄들에서 실제로 무엇이 달라진 것 같아?

[과외냥이 설명 — 모기가 본 뒤]
<주인·이벤트·전후 값·증명 범위>

[아직 안 본 파일 — 모기가 샛길 선택]
- ...
```

## 파일럿에서 짧게 남길 것

세션을 끝낼 때 아래만 이 문서의 `## 실행 기록`에 append한다. 시간을 재거나 질문 수를 점수화하지 않는다.

- 실제로 본 핵심길: 어느 SHA 범위의 어느 hunk였나
- 샛길: 모기가 어느 파일을 골랐고 새 질문·발견이 있었나, 또는 미관찰
- 마찰: 너무 적음·적당함·너무 많음 중 모기가 직접 표현한 것
- 다음 회차에서 한 가지만 바꿀 것

## 파일럿 뒤 판단할 것

- PR 카드와 code diff note를 계속 별도 선택지로 둘지, 같은 PR 학습 묶음으로 연결할지
- 핵심길의 기본 단위를 구현 1개+테스트 1개로 둘지
- fix 전후 비교를 모든 review fix의 기본값으로 올릴지
- 샛길 파일 선택이 실제로 예상 밖의 질문을 만드는지
- 이 흐름을 프리앰블의 영구 규칙으로 승격할지, 선택 모드로 남길지
