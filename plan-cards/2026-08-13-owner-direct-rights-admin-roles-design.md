# 카드 — 원작자 직접권 + 어드민 역할 테이블 설계안 (sw-c2p + sw-qd5, 착수 전 설계 카드)

작성: 냐옹이 Gen 6, 2026-08-13. 원문 SSOT: sw-c2p·sw-qd5 이슈 + 이 카드의 브레인스토밍 대화. PR 아직 없음 — **과외냥이 점검용 설계안**이다. 계약 작성 전 단계이며, 점검 결과는 환류 메모함(master-delivery-memos.md)으로.

## 현행 실물 (마스터 측정, 2026-08-13)

- 발색샷 수정·삭제 RLS는 전부 **등록자(created_by) 기준** (20260803100000). 귀속의 진실은 owner_uid가 됐지만(PR #495/#496) spec 결정 3이 직접권을 "코어 운영 경험 후 별도 결정"으로 미뤄놨고, 원작자가 가진 건 `request_swatch_removal`(내려주세요 표식 RPC)뿐. 표식을 세워도 사진은 어드민 처리 전까지 **계속 공개**.
- swatches에 **가시성 개념 자체가 없음** — 공개/비공개 컬럼 없이 전면 공개 읽기(anon_read).
- `is_admin()` = 마이그레이션에 **개인 이메일 4개 평문 하드코딩** (20260428230000). 어드민 교체 = DB 배포, 이메일 코드 이력 영구 잔존. 의존처: 마이그 42개 파일 + 앱 코드 (시그니처 유지 시 재정의 한 번으로 전파).
- 삭제는 항상 되는 게 아님: comparison_assessments의 evidence 인용이 `ON DELETE RESTRICT` — **인용된 발색은 삭제가 DB에서 막힌다**. 비교 노트 연결은 CASCADE(삭제 시 남의 노트에서 근거가 조용히 증발).
- 어드민의 발색 수정·삭제 override 정책은 이미 존재 (20260510050000) — 이번 설계가 어드민 발색 권한은 안 건드림.
- 인용 자격 `is_own_observation_swatch` = 원작자 OR 등록자 — 승인된 기존 설계(귀속 이전 ≠ 등록자 인용 자격 박탈).

## 설계안

### §1. 직접권: 판정 기준을 owner_uid로 단일화

swatches의 수정·삭제 RLS 정책(`update_owner`/`delete_owner`)과 swatch_items의 부모-소유자 정책 판정을 `created_by = auth.uid()` → **`owner_uid = auth.uid()`로 교체**.

- 이전 안 된 발색: owner_uid = created_by라 동작 불변.
- 이전된 발색: 원작자가 직접 수정·삭제 가능, **등록자 권한은 자동 회수** (모기 결정).
- un-verify 시 owner_uid가 created_by로 원복되는 기존 설계 덕에 **권한도 자동 원복**.
- 레거시 owner_uid NULL 행: 아무에게도 안 잡힘 (현행 created_by NULL 행과 동일 동작, 기존 부채 방침 그대로).
- 인용 자격(원작자 OR 등록자)은 불변.

### §2. 비공개 토글: swatches.hidden_at 신설

`hidden_at timestamptz` (NULL = 공개). `removal_requested_at`과 같은 표식 패턴.

- 공개 읽기 정책에 `hidden_at IS NULL` 필터 추가. 비공개 행은 본인(owner_uid)과 어드민만 SELECT.
- 토글은 별도 RPC 불요 — §1로 원작자가 UPDATE 권한을 가지므로 일반 업데이트로 충분 (owner_uid 변조는 기존 보호 트리거가 막음).
- 남의 비교 노트에 인용된 비공개 발색의 표시 처리(자리표시 등)는 구현 계획에서 확정할 UI 세부.
- 주의: 공개 읽기 정책 변경 = **RLS 정책 스냅샷 제도의 첫 진짜 정책 변경 PR** — 사람말 요약 코멘트 첫 실전 확인 기회.

### §3. 삭제 요청 동선: 폐기 아닌 용도 축소

직접 삭제·비공개가 생기면 요청의 남는 용도는 하나 — **인용에 잠겨(RESTRICT) 삭제가 막힌 발색의 어드민 정리 요청**. `request_swatch_removal` RPC와 어드민 큐 유지, 의미를 이걸로 재정의. UI 동선: 삭제 시도 → 인용 잠김이면 "비공개 전환 + 정리 요청" 제안. "처리 전까지 계속 공개" 갭(과외냥이 지적)은 §2가 원천 봉쇄.

### §4. 어드민 역할 테이블: admin_users

`admin_users(user_id uuid PK → auth.users, granted_at, note)` 신설, `is_admin()`을 이메일 대조 → `auth.uid()` 멤버십 조회로 재정의.

- 함수 시그니처 불변 → 의존처 전파는 재정의 한 번.
- 시드: 현행 어드민 4명 uid를 auth.users에서 이메일로 조회해 삽입. 이후 교체부터는 행 삽입·삭제만 (배포 불요, 이메일 잔존 없음).
- admin_users는 클라이언트 비노출 (정책 없음 + GRANT 회수) — is_admin()이 SECURITY DEFINER라 함수만 접근.
- 어드민 관리 UI는 안 만듦 (YAGNI) — 추가·제거는 Studio/SQL.

### 범위 밖 (기록만)

- `user_profiles.is_core` 이름 혼동은 이 레인에서 안 건드림 (별도 이슈감).
- RLS 좁히기 본체(sw-tw7) 게이트("유저 직접 수정 필드 추가") 해당 여부는 착수 전 확인 — 해당해도 이 설계는 독립 진행 가능.
