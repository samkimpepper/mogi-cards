## 1. 뭐가 생겼나 `[READ]`

- `[READ]` 운영자가 코어에게 보내는 링크 (DM·메일·슬랙) 에 `src=<채널>` 을 붙일 수 있게 됐다 — `?shade=<id>&src=dm`. 세션 유입 판정에 `notification` 출처가 새로 생겨서, METRICS-05 가드레일 (외부 알림 비율 50% 초과 시 그 주 WAC 무효) 이 이제 운영자 발송분과 코덕끼리 공유를 구분한다. Phase 6 알림 발송 **전에** 들어가야 했던 게 이 지점이야 — 발송 시작 후엔 과거 유입을 소급 분류할 수 없거든.
- `[READ]` 판정 순서에서 `src` 가 `shade` 를 **이긴다**. 알림 링크는 shade 랑 src 를 둘 다 달고 오는데, shade 를 먼저 보면 운영자 발송이 전부 코덕 공유 (`shared_link`) 로 잡혀서 이 작업 전체가 무의미해진다.
- `[READ]` 주간 집계 SQL (`wac_weekly.sql`) 의 외부 세션 IN 목록에도 `notification` 이 들어갔고, 이게 빠지면 어떻게 되는지를 잡는 SQL fixture (50% 경계 양면) 가 같이 생겼다.

## 2. 설계에서 배울 것 `[READ]`

- `[READ]` **Codex 가 "허용값 3종 (dm/mail/slack) 만 인정하자" 고 했는데 기각했어.** 임의값 (`?src=아무거나`) 을 다 알림으로 치면 스푸핑이 외부 비율을 **부풀리고** (→ 가드레일이 더 자주 발동 = WAC 를 더 자주 무효화 = 보수 방향), 반대로 엄격 검증은 운영자 오타 (`?src=DM` 대문자) 를 organic 으로 **흘린다** (→ 외부 유입이 과소집계 = 부풀려진 WAC 가 valid 로 통과 = 위험 방향). 측정 가드는 두 실패 방향이 대칭이 아니야 — 어느 쪽으로 틀리는 게 덜 아픈지를 먼저 정하고 검증 강도를 골라야 한다. 빈 `?src=` 만 걸렀다.
- `[READ]` **값은 읽되 저장하지 않는다.** 채널값 (dm/mail) 을 그대로 이벤트에 실으면 "URL 쿼리 내용을 props 로 안 넘긴다" 는 T-05-08 계약이 깨져서, 고정값 `notification` 하나로 접었다. "DM 이 메일보다 잘 먹혔나" 를 보고 싶어지면 그때 별도 결정이 필요하다 (열린 결정로 남김).
