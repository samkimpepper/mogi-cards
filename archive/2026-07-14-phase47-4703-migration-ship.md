## 1. 무슨 일이 있었나 `[READ]`

- `[READ]` **옛 장부가 로컬 DB 에서 실제로 지워졌다.** 삭제 migration (`20260713000000_remove_legacy_trait_mirrors.sql`) 이 로컬 docker 에 딱 1회 적용됐고, 옛 테이블 7개·`form_id`/`finish_id` 컬럼·두 장부를 맞춰주던 자동 장치(trigger 10개·함수 14개)·옛 전용 권한이 사라졌다. 새 장부(traits 계열)와 그 정책·검증 함수는 그대로 살아 있다.
- `[READ]` **지우기 전에 "두 장부 내용이 완전히 같은가" 대조를 통과했다 (차이 0건).** 이 대조는 migration 파일 안에 들어 있어서, 나중에 원격에 push 할 때 **원격의 진짜 데이터로 한 번 더 자동으로 돈다.** 원격에서 한 건이라도 다르면 migration 이 스스로 멈추고 아무것도 안 지운다 (fail-closed). 그러니까 "로컬에서 통과했으니 원격도 안전" 이 아니라, **원격 push 순간이 진짜 시험**이다.
- `[READ]` **역할별 권한도 검사했다.** 손님(익명)은 읽기만 되고, 로그인 유저의 무단 쓰기는 거부되고, 어드민의 "사용 중지"는 기존 연결(라인·shade·규칙)을 안 건드린다는 것까지 SQL 검사(`phase47_trait_cleanup_verify.sql`)로 통과. 검사용 가짜 데이터는 전부 되돌렸고 migration 은 안 건드렸다.
- `[READ]` **별도 검증 에이전트(verifier)가 요약을 안 믿고 코드·DB 를 직접 다시 봤다.** 결과 = 기준 17개 전부 통과, 갭 0 (`47-VERIFICATION.md`). 남긴 것은 전부 "사람이 봐야 하는 것"(UAT)으로 분류됨.
- `[READ]` **로컬 docker 의 기존 버그를 하나 발견했다** (이번 작업 탓 아님): 권한이 없는 함수를 익명으로 실제 호출하면 로컬 DB 프로세스가 죽는다. 그래서 "익명 호출 → 42501 거부" 확인만 로컬에서 라이브로 못 했고, 권한 장부 조회로 대체 검증했다. **원격 push 후에 실제 호출 한 번 해봐야 한다.**

## 2. 새로 나온 말

| 말 | 쉬운 뜻 | 이번 예시 |
|---|---|---|
| parity 감사 (0건 대조) | 지우기 직전에 새 장부와 옛 장부 내용이 완전히 같은지 세는 검사 | 로컬 0건 통과. 원격 push 때 같은 검사가 다시 돈다 |
| 42501 | "권한이 없어서 거부됐다"는 Postgres 에러 번호 | 익명이 trait 쓰기 RPC 를 부르면 이 에러가 나야 정상 |
| segfault | 프로그램이 그 자리에서 죽어버리는 치명 오류 | 로컬 docker 에서 권한 없는 함수를 부르면 발생 (기존 버그) |

## 3. UAT 하면서 직접 봐야 할 것

- **화면 결과는 예전과 똑같아야 한다.** 카탈로그 마감 라벨, 수정 시트 미리 채우기, 질감 칩. 다르게 보이면 그게 버그 — 바로 보고.
- **UAT 1~3·5번은 migration 적용된 로컬 docker 를 보면서** 한다 (env 전환은 모기 본인만, 끝나면 되돌리기). 원격(QA)을 보면 옛 테이블이 아직 살아 있어서 검사가 헛돈다.
- **뭔가 꼬여도 migration 을 되돌리면 안 된다.** 로컬이 이상해지면 `supabase db reset` 으로 처음부터 다시 맞추는 게 정답.
