## 모기 답변 — 과외 중 구술 정리

- **M1.** travelog는 사람이 남길 가치가 있다고 고른 사건만 만드는 선별 기록이고, 세션 JSONL은 매 세션의 주입과 Read 툴 호출이 자동으로 남는 전수 로그다. 라우터의 실제 주입·순응을 빠짐없이 세려면 JSONL이 맞다.
- **M2.** 에이전트가 팩을 주입 전에 스스로 읽고, 관련 파일을 건드릴 때 안내가 주입된 뒤 팩을 다시 읽을 수 있다. 옛 측정기는 첫 Read만 기억해서 주입 뒤 Read를 놓쳤고, 실제로 순응한 세션을 미순응으로 오판했다. 그러면 순응률을 실제보다 낮게 보고 안내가 부족하다고 착각해 팩 전문 강제 주입 같은 과한 결정을 내릴 수 있다.

## Appendix — 주입 전에 읽었는데 왜 주입 뒤에도 다시 읽나

여기서 **주입은 팩 내용 자체를 자동으로 넣는 행동이 아니라, "이 팩을 읽어라"라는 짧은 안내**다. 실제 팩 내용은 에이전트가 별도의 Read 툴 호출로 읽는다.

에이전트는 주입이 없어도 코어 라우팅 표를 따르거나, 조사 중 작업 성격을 알아채거나, 같은 세션의 앞선 요청에서 팩을 자발적으로 읽을 수 있다. 그 뒤 `supabase/migrations/**` 같은 관련 파일을 수정하려 하면 PreToolUse 라우터가 경로를 보고 안내를 주입한다. 라우터는 자기가 이미 주입했는지는 기억하지만, 에이전트의 자발적 Read까지 감시해 주입을 취소하지는 않는다.

```text
순번 10: 에이전트가 db-migration 팩을 자발적으로 Read
순번 20: DB 파일 수정 직전, 라우터가 "db-migration 팩을 읽어라"고 주입
순번 30: 에이전트가 안내를 받고 같은 팩을 다시 Read
```

실제로는 순번 30이 있으므로 안내에 순응한 세션이다. 그러나 옛 측정기는 팩별 첫 Read인 순번 10만 저장하고 순번 30을 버렸다. `10 > 20`이 아니므로 "주입 뒤 Read 없음"이라고 잘못 판정한 것이다.

수정된 측정기는 Read 순번 전부를 `[10, 30]`처럼 저장하고, 주입 순번보다 뒤인 Read가 하나라도 있으면 순응으로 판정한다. 이 수정은 순응률이 거짓으로 낮아져 라우터를 불필요하게 무겁게 만드는 오결정을 막는다.
