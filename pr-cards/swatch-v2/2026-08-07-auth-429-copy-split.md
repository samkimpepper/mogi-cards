## 모기 답변 — 과외 중 구술 정리

- **A1.** 서버의 시간당 한도 문구가 바뀌어 매치에 실패하면 새 013이 아니라 기존 002로 가서 "1분 뒤 다시 시도"가 뜬다. 안내 개선은 사라지지만 PR 전의 기존 동작으로 돌아가는 것이고, 모르는 문구를 시간당 한도라고 새로 오분류하지 않으므로 회귀가 아닌 안전한 퇴보다.
- **A2.** GoTrue가 두 원인에 같은 코드를 줘서 실제 응답에서 문구만 유일한 구분 신호다. 또 "문구를 보지 말고 code만 보라"는 규칙은 우리가 SQL 오류 코드를 갈라 고칠 수 있는 Postgres/PostgREST 데이터 오류용이며, 코드 설계를 바꿀 수 없는 외부 GoTrue Auth 오류에 그대로 적용되는 규칙은 아니다.

## Appendix — 왜 Postgres는 문구를 보면 안 되고 GoTrue Auth는 예외인가

중요한 경계는 "문구 파싱은 언제나 나쁘다"가 아니라 **오류 코드를 누가 통제할 수 있는가**다.

| 오류 출처 | 우리가 서버 코드를 바꿀 수 있나 | 같은 코드가 두 뜻이면 |
|---|---|---|
| Postgres/PostgREST 데이터 오류 | 가능 — 저장소의 SQL·RPC를 우리가 관리함 | SQL에서 서로 다른 전용 SQLSTATE로 갈라야 함. 자유로운 사람용 문구 파싱은 금지 |
| GoTrue Auth 오류 | 불가능 — 외부 인증 서버의 응답 계약 | code가 같고 msg만 다르면, 실측된 고정 문구를 제한적으로 볼 수밖에 없음 |

이번 예외가 무제한 문구 파싱 허용은 아니다. 시간당 한도의 실측 고정 문구만 positive match하고, 알 수 없는 문구는 기존 002로 돌린다. 즉 외부 서버의 부족한 코드를 보완하되 추측 범위는 가장 작게 유지한다.
