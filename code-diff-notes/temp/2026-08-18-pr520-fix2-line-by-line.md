## 1. 느린 Storage 작업 하나가 전체 배치를 붙잡던 문제

### 먼저 상황

서버 함수 한 번이 할 일은 크게 두 묶음이었다.

```text
첫 번째: 숨김·복구·삭제 작업표 소비
두 번째: 실패했던 사진 복사 재시도
```

fix1은 각 묶음에 시간 예산을 줬다.

```text
수명주기 소비: 4초
사진 복사 재시도: 8초
```

그런데 배포 함수 전체 실행 상한은 당시 10초로 계산하고 있었다.

```text
4초 + 8초 = 12초
함수 전체 상한 = 10초
```

- [x] 두 작업의 시간 예산을 따로 정했지만, 합계는 함수 전체 수명보다 길었다.

### 숨은 문제 하나 더

4초 검사는 Storage 작업을 **시작하기 전**에만 실행됐다.

```text
현재 경과 시간 3.9초
→ 아직 4초 전이므로 move 시작
→ Storage가 20초 동안 응답하지 않음
```

작업을 시작한 뒤에는 그 요청을 끊을 장치가 없었다.

- [ ] 시작 전에 시간이 남았다는 사실은 그 작업이 시간 안에 끝난다는 보장이 아니다.

### fix2가 바꾼 것

수명주기용 Storage 요청 하나마다 1.2초 상한을 붙였다.

한 작업이 최대 세 번 Storage를 호출할 수 있다고 계산했다.

```text
move 1회
+ 목적지 존재 확인 1회
+ 출발지 존재 확인 1회
= 최대 3회

1.2초 × 3회 = 3.6초
```

따라서 작업 하나가 수명주기 예산 4초를 혼자 넘겨 쓰지 못하게 했다.

- [x] 1.2초 제한은 모든 사진 다운로드가 아니라 수명주기용 Storage 호출에 붙었다.
- [x] 느린 요청은 무한히 기다리지 않고 중단한 뒤 다음 재시도 기회를 남긴다.

### 공통 마감 시각

함수 마지막 정리와 응답을 위해 1초를 남겼다.

```text
전체 실행 상한 10초
- 마무리 여유 1초
= 작업 공통 마감 9초
```

수명주기 소비가 2초를 썼다면 사진 재시도는 원래 몫 8초를 전부 받지 않는다.

```text
공통 마감까지 남은 시간 7초
사진 재시도 예산 = min(원래 8초, 남은 7초)
```

- [ ] 두 작업이 각각 자기 시계를 보는 대신 같은 종료 시각을 바라보게 됐다.
- [x] 앞 작업이 오래 걸리면 뒤 작업은 남은 시간만 사용한다.

### fix2에서 아직 완결되지 않은 것

fix2는 새 사진 작업을 시작할지 판단하는 시간 계산은 고쳤다.

그러나 이미 시작한 사진 다운로드·업로드에 남은 시간을 끝까지 전달하지는 못했다.

그 잔여 문제는 fix3에서 이어서 고쳤다.

- [x] fix2의 시간 수리는 방향은 맞았지만 이 라운드에서 완전히 끝난 것은 아니다.

## 2. 사진 복구가 전부 실패했는데 성공으로 보이던 문제

### HTTP 200의 실제 뜻

HTTP 200은 서버가 요청을 받아 결과를 정상적으로 돌려줬다는 뜻이다.

사진 복사 자체가 성공했다는 뜻은 아니다.

예를 들어 서버가 이렇게 답할 수 있었다.

```text
HTTP 상태: 200
처리한 사진: 3장
복사 성공: 0장
```

- [x] `요청 처리 성공`과 `사진 복사 성공`은 서로 다른 사건이다.

### 변경 전

복구 버튼은 이것만 확인했다.

```ts
return res.ok
```

따라서 사진 세 장이 전부 실패해도 HTTP가 200이면 성공으로 판단했다.

- [x] 변경 전 화면은 응답 본문을 읽지 않고 HTTP 상태만 봤다.

### 변경 후

fix2는 실제 처리 건수와 복사 성공 건수를 읽었다.

```ts
if (!res.ok) return false

const attempted = Array.isArray(body?.results) ? body.results.length : 0
const copied = typeof body?.copied === 'number' ? body.copied : 0
return attempted === 0 || copied > 0
```

사례별 결과는 이렇다.

```text
대상 3장 / 성공 0장
→ 실패
→ 버튼 다시 활성화
→ 사용자가 다시 시도 가능

대상 3장 / 성공 1장 이상
→ 실제 진전이 있으므로 성공

대상 0장
→ 이미 복사할 것이 없는 상태이므로 실패 아님
```

- [x] 사진이 전부 실패하면 HTTP 200이어도 복구 실패로 표시한다.
- [x] 처리 대상이 0장인 것은 실패가 아니라 이미 할 일이 없는 상태다.

### 이 항목의 판정

이 문제는 fix2에서 완전히 닫혔다.

## 3. 데이터 읽기 실패를 `발색 0개`로 보여주던 문제

### 변경 전

발색이나 격리 판정 자료를 읽다가 오류가 나면 저장소 함수가 `{}`를 돌려줬다.

그런데 화면에서 `{}`는 이미 이런 뜻이었다.

```text
정상적으로 읽었음
+ 등록된 발색이 정말 0개임
```

따라서 서로 다른 두 상태가 같은 값이 됐다.

```text
정상 빈 상태 → {}
데이터 읽기 실패 → {}
```

- [x] 변경 전에는 정상 빈 상태와 서버 오류를 반환값으로 구분할 수 없었다.

### 사용자에게 보이던 결과

화면은 오류가 난 줄 모르고 빈 목록을 저장했다.

사용자 눈에는 원래 있던 발색이 모두 사라진 것처럼 보일 수 있었다.

- [x] 실제 데이터가 삭제된 것이 아니라, 읽기 실패가 빈 목록처럼 표시된 것이다.

### 변경 후

fix2는 실패를 `{}`로 바꾸지 않고 오류로 올렸다.

```text
진짜 발색 0개
→ 정상 빈 화면

발색 또는 격리 자료 읽기 실패
→ 오류 화면
→ 재시도 가능
```

- [x] 성공한 빈 결과는 값으로 돌려주고, 실패는 오류 신호로 올린다.
- [x] 화면은 오류와 정상 빈 상태를 다르게 표시한다.

## 4. 고장 난 작업 20개가 뒤 작업을 계속 막던 문제

### 작업표의 기본 동작

수명주기 작업표는 오래된 작업부터 한 번에 최대 20개를 가져왔다.

```text
1번 작업
2번 작업
...
20번 작업
21번 작업
```

### 변경 전 문제

Storage 설정 오류처럼 영원히 처리할 수 없는 작업 20개가 앞에 있으면 매 주기 같은 일이 반복됐다.

```text
첫 배치 → 고장 난 1~20번 선택
다음 배치 → 다시 고장 난 1~20번 선택
다음 배치 → 또 고장 난 1~20번 선택
```

21번 뒤에 들어온 정상 숨김·삭제는 차례를 받지 못했다.

- [x] 실패 작업을 무한히 즉시 재선택하면 정상 작업까지 굶을 수 있다.

### fix2가 기록하기 시작한 값

각 작업표 행에 다음 세 값을 붙였다.

```text
attempts        실제 시도 횟수
last_attempt_at 마지막 시도 시각
last_error      마지막 실패 사유
```

- [x] 작업을 목록에서 가져온 횟수가 아니라 실제로 처리해본 횟수를 센다.

### 재시도 간격

사진 복사 재시도와 같은 간격 규칙을 재사용했다.

```text
첫 실패 → 15분 뒤
다음 실패 → 1시간 뒤
다음 실패 → 6시간 뒤
4회 소진 → 자동 선택에서 제외
```

고장 난 행은 작업표에서 즉시 삭제하지 않는다.

같은 파일에 대해 뒤따르는 복구·삭제 순서를 뒤집지 않기 위해 자리는 남긴다.

대신 다른 파일의 작업표 20칸을 계속 차지하지 않게 한다.

- [x] 4회 소진 행은 큐에 남지만 자동 처리 대상으로 계속 뽑히지는 않는다.
- [x] 같은 파일의 작업 순서는 막되, 다른 파일 작업까지 계속 굶기지는 않는다.

### fix2 뒤에 남은 것

4회 소진 행을 운영자가 알아차릴 자동 경고가 부족했다.

## 5. 같은 URL이라는 이유로 관계없는 대표사진까지 회수하던 문제

### 여기서 `URL 폴백`의 뜻

이 절의 `폴백`은 화면에서 대체 사진을 보여준다는 뜻이 아니다.

대표사진과 사본의 관계가 끊긴 옛 데이터에서 URL 문자열을 비교해 관계를 추정하는 안전망이다.

- [x] 이 절의 URL 폴백은 표시용 대체 이미지가 아니라 레거시 관계 추정 방식이다.

### 왜 URL 하나를 여러 발색이 쓸 수 있나

비교 단체 사진 한 장에는 여러 색이 함께 나올 수 있다.

같은 사진 URL을 여러 발색과 shade가 정상적으로 공유할 수 있다.

```text
발색 A → group.jpg
발색 B → group.jpg
빨강 shade 대표 → group.jpg
분홍 shade 대표 → group.jpg
```

- [x] 같은 URL을 여러 발색이 쓰는 것은 항상 중복 오류가 아니라 정상 단체 사진일 수도 있다.

### 변경 전 문제

발색 A의 사진 사본을 삭제할 때 URL이 같은 대표사진을 전역에서 찾았다.

```text
삭제되는 URL = group.jpg
→ DB 전체에서 group.jpg 대표를 찾음
→ 관계없는 분홍 shade 대표까지 회수할 수 있음
```

발색 B가 같은 사진을 계속 사용하고 있어도 그 사실을 확인하지 않았다.

- [x] URL 문자열이 같다는 사실만으로는 그 대표사진의 근거가 사라졌다고 단정할 수 없다.

### fix2가 추가한 세 경계

#### 경계 1 — 발색과 shade의 실제 연결

삭제되는 사진의 발색이 그 shade와 실제로 연결돼 있을 때만 URL 추정을 사용한다.

- [x] 무관한 shade는 같은 URL이라는 이유만으로 회수 대상이 되지 않는다.

#### 경계 2 — 같은 URL의 생존 사본

다른 발색이 같은 URL의 사본을 아직 가지고 있으면 대표사진을 회수하지 않는다.

```text
발색 A의 group.jpg 삭제
+ 발색 B의 group.jpg 생존
→ 사진 근거가 아직 있으므로 대표 유지
```

- [x] 같은 URL을 쓰는 마지막 사본이 사라질 때만 URL 기반 회수 근거가 생긴다.

#### 경계 3 — 어드민 수동 대표 자리

어드민이 직접 지정한 `manual` 대표는 자동 규칙이 다른 사진으로 바꾸지 않는다.

사본 관계만 끊고 대표 행의 자리는 남긴다.

깨진 URL을 고치는 것은 이후 어드민 데이터 정리의 몫으로 남긴다.

- [x] 자동 재선정은 어드민의 명시적 대표 선택을 대신 뒤집지 않는다.

### fix2에서 아직 완결되지 않은 것

발색 A와 B가 같은 URL을 쓰고 있고 두 발색이 동시에 삭제되면 문제가 남았다.

두 삭제가 서로를 동시에 바라보면 각각 이렇게 판단할 수 있다.

```text
A 삭제: B가 아직 있으니 대표 유지
B 삭제: A가 아직 있으니 대표 유지
```

결과적으로 둘 다 사라졌는데 대표는 죽은 URL을 가리킬 수 있었다.

이 동시 삭제 경합은 fix3에서 같은 URL 작업을 한 번에 하나씩 처리하도록 보강했다.

- [x] fix2는 평상시 범위를 좁혔지만 동시 삭제까지 완전히 직렬화하지는 못했다.

>
> 비교발색샷이 대표사진일수 있으니까 여러 쉐이드에 매핑되어있을수 있음.
