# 모기 code diff note — PostgreSQL `SELECT` 권한과 RLS의 두 관문

날짜: 2026-08-12

재료: swatch-v2 PR #501 · `supabase/POLICY-SNAPSHOT.md` · 정책 스냅샷 생성기

## 모기의 질문

> `pg_class`, `pg_policies`, 권한 정보 세 개 다 권한이 있다는 쪽을 가리켜야 조회 가능한가? 필요충분조건인가?

## 한 줄 결론

아니다. 세 정보는 같은 종류의 허용 신호가 아니다. 일반 사용자가 기본 테이블을 직접 조회하는 경우, PostgreSQL은 먼저 `GRANT`로 **명령을 시도할 자격**을 확인하고, RLS가 켜져 있으면 정책으로 **결과에 어느 행을 보여줄지** 결정한다.

```text
1. 그 사용자에게 SELECT 권한이 있는가?
   ├─ 없음 → 권한 오류
   └─ 있음 → 2번

2. 대상 테이블의 RLS가 켜져 있는가?
   ├─ 꺼짐 → RLS 정책을 적용하지 않고 조회
   └─ 켜짐 → 3번

3. 조회하려는 행이 적용 대상 RLS 정책들을 통과하는가?
   ├─ 통과 → 그 행이 보임
   └─ 실패 → 그 행은 안 보임
```

특히 아래 상황을 구분한다.

```text
SELECT 권한 있음
RLS 켜짐
그 사용자에게 적용되는 PERMISSIVE SELECT 정책 없음
→ SELECT 문 자체는 실행될 수 있지만 기본 거부가 적용돼 결과에 행이 나타나지 않음
```

이 때문에 RLS에서 막혔을 때 권한 오류 대신 `0 rows`처럼 보였던 기억이 설명된다. `GRANT` 관문은 이미 통과했고, RLS가 명령을 금지하기보다 결과에 보일 행을 걸러냈기 때문이다.

## 세 정보의 역할

| 정보 출처 | 값의 주인 | 답해주는 질문 |
|---|---|---|
| 권한 정보 | 역할이 대상 테이블에서 받은 권한 | 이 역할이 `SELECT` 명령을 시도할 자격이 있는가? |
| `pg_class` | 대상 테이블 | 이 테이블에서 RLS 검사를 작동시키는가? |
| `pg_policies` | 대상 테이블에 붙은 개별 정책 | RLS가 작동할 때 어떤 역할·명령·행을 허용하거나 제한하는가? |

`pg_class.relrowsecurity = true`는 허용 신호가 아니라 **RLS 검사 장치가 켜졌다는 뜻**이다. `pg_policies`에 정책이 존재한다는 사실만으로도 부족하다. 그 정책의 대상 역할과 명령, 행 조건, `PERMISSIVE`·`RESTRICTIVE` 정책의 조합까지 맞아야 특정 행이 보인다.

일반 사용자의 기본 테이블 직접 조회로 범위를 한정하면, 특정 행이 보이는 조건은 대략 다음과 같다.

```text
SELECT 자격
AND
(
  RLS가 꺼져 있음
  OR
  그 행이 적용 대상 RLS 정책 조합을 통과함
)
```

테이블 소유자, `BYPASSRLS`, 관리자 권한, `SECURITY DEFINER` 함수나 뷰를 통한 경로는 별도로 계산해야 한다.

## PR #501의 사람말 요약이 지켜야 할 선

`authenticated` 대상의 `SELECT` 정책이 추가됐다는 사실만 보고 “로그인 사용자가 이제 조회할 수 있다”고 쓰면 안 된다.

- 말할 수 있음: `authenticated`의 `SELECT`를 허용하는 RLS 정책이 추가됨
- 아직 단정할 수 없음: 로그인 사용자가 실제로 대상 행을 조회할 수 있게 됨

실효 접근은 `GRANT`, 테이블의 RLS 활성 상태, 해당 행의 정책 조건, 다른 `RESTRICTIVE` 정책과의 조합에 달려 있다. 정책 스냅샷은 이 구조를 리뷰할 수 있게 펼쳐 보이는 도구이지, 보안 구조 전체의 안전 인증서가 아니다.
