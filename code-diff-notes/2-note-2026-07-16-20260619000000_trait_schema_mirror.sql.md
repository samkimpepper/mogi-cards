## `CHECK (type IN (...))`

```sql
type text NOT NULL CHECK (type IN ('form', 'finish', 'finish_detail', 'texture'))
```

- 실제 컬럼 타입은 `text`다.
- 네 문자열 중 하나만 저장할 수 있다.
- 목록 밖 값이 들어오면 PostgreSQL이 저장을 거절한다.
- PostgreSQL의 별도 `ENUM` 타입을 만든 것이 아니라 `text + 허용 목록 검사` 방식이다.

### Spring/JPA enum과 비교

```java
enum TraitType {
    FORM, FINISH, FINISH_DETAIL, TEXTURE
}

@Enumerated(EnumType.STRING)
private TraitType type;
```

- JPA enum은 Java 객체 단계에서 허용값을 제한한다.
- SQL의 `CHECK`는 애플리케이션 밖에서 직접 SQL을 실행해도 DB가 마지막에 검사한다.
- 둘을 함께 사용하면 애플리케이션과 DB 양쪽에서 잘못된 값을 막을 수 있다.

### MSSQL에서는

MSSQL도 `CHECK` 제약조건을 지원한다.

```sql
CREATE TABLE traits (
    type nvarchar(30) NOT NULL,
    CONSTRAINT CK_traits_type
        CHECK (type IN ('form', 'finish', 'finish_detail', 'texture'))
);
```

- 목록 밖 값을 `INSERT`하거나 `UPDATE`하면 MSSQL이 거절한다.
- MSSQL에는 별도의 `ENUM` 타입이 없다.
- 간단한 고정 목록은 `nvarchar + CHECK`, 설명이나 관리 기능이 필요한 목록은 코드 테이블과 외래키를 주로 사용한다.

## `PRIMARY KEY` 인덱스와 `parent_trait_id` 인덱스

```sql
id              bigserial PRIMARY KEY,
parent_trait_id bigint REFERENCES traits(id)

CREATE INDEX idx_traits_parent ON traits(parent_trait_id);
```

### PostgreSQL도 PK 인덱스를 자동으로 만드는가

맞다. PostgreSQL은 `PRIMARY KEY (id)`를 만들면 `id`에 고유 B-tree 인덱스를 자동 생성한다.

이 인덱스는 다음을 보장하고 돕는다.

- `id` 중복 방지
- `id`로 행 찾기
- 다른 테이블이나 컬럼이 `traits(id)`를 외래키로 참조할 때 부모 행 확인

### 그런데 왜 `parent_trait_id` 인덱스를 따로 만드는가

PK 인덱스와 `parent_trait_id` 인덱스는 방향이 다르다.

- PK 인덱스: 부모의 `id`를 빠르게 찾는다.
- `idx_traits_parent`: 특정 부모를 가리키는 자식들을 빠르게 찾는다.

PostgreSQL은 외래키가 참조하는 부모 컬럼 `traits(id)`에는 PK 인덱스가 있는지 요구하지만, 자식 쪽 외래키 컬럼 `parent_trait_id`의 인덱스는 자동 생성하지 않는다. 따라서 필요하면 직접 만든다.

이 마이그레이션에서는 다음 작업에 도움이 된다.

```sql
SELECT *
FROM traits
WHERE parent_trait_id = 10;
```

- 어떤 `finish` 아래에 속한 `finish_detail` 목록 찾기
- 부모 trait를 삭제하거나 PK를 변경할 때, 그 부모를 참조하는 자식이 있는지 확인하기

trait 종류가 매우 적다면 당장 체감 성능 차이는 작을 수 있다. 그래도 부모에서 자식으로 조회하는 관계가 명확하므로 별도 인덱스를 둔 것으로 볼 수 있다.

## `parent_trait_id`는 매핑 테이블 연결용인가

아니다. `parent_trait_id`는 `traits` 테이블 안에서 다른 trait를 가리키는 자기 참조 외래키다.

```text
traits
id=10, type=finish,        slug=glossy,    parent_trait_id=NULL
id=11, type=finish_detail, slug=wet_gloss, parent_trait_id=10
```

- `parent_trait_id`: trait와 trait 사이의 부모·자식 관계
- `line_traits.trait_id`: 제품 라인과 trait의 연결
- `shade_traits.trait_id`: 개별 shade와 trait의 연결

## trigger 함수의 `NEW`

`NEW`는 함수 괄호에 명시한 인자가 아니다. PostgreSQL이 행 단위 trigger를 실행할 때 자동으로 제공하는 특별 변수다. DB에 최종 저장되기 직전의 새 행 전체를 담는다.

### `INSERT` 예시

```sql
INSERT INTO traits (type, slug, parent_trait_id)
VALUES ('finish_detail', 'wet_gloss', 10);
```

trigger 안에서는 다음처럼 읽을 수 있다.

```text
NEW.type            = 'finish_detail'
NEW.slug            = 'wet_gloss'
NEW.parent_trait_id = 10
```

### `UPDATE` 예시

```sql
UPDATE traits
SET parent_trait_id = 20
WHERE id = 11;
```

- `OLD.parent_trait_id`: DB에 저장돼 있던 기존 값
- `NEW.parent_trait_id`: 이번에 바꾸려는 새 값

작업별 사용 가능 값:

- `INSERT`: `NEW`
- `UPDATE`: `OLD`, `NEW`
- `DELETE`: `OLD`

이 마이그레이션의 `validate_trait_parent()`는 `NEW` 값을 검사하고 `RETURN NEW`를 실행해 그 행을 저장 단계로 넘긴다.

## `SELECT ... INTO`로 변수에 조회값 넣기

```sql
SELECT type INTO parent_type
FROM traits
WHERE id = NEW.parent_trait_id;
```

여기서 역할은 다음과 같다.

- `type`: `traits` 테이블의 컬럼
- `parent_type`: 위의 `DECLARE`에서 만든 PL/pgSQL 변수
- 조회한 부모 trait의 `type` 값을 `parent_type` 변수에 넣는다.

MSSQL로 바꾸면 다음과 비슷하다.

```sql
SELECT @parent_type = type
FROM traits
WHERE id = @parent_trait_id;
```

PostgreSQL의 `SELECT 컬럼 INTO 변수`와 MSSQL의 `SELECT @변수 = 컬럼`은 쓰는 순서가 다르다.

이 조회는 `id`가 PK라 결과가 최대 한 행이다. 부모 행이 없으면 PostgreSQL의 `parent_type`은 `NULL`이 되고, 이어지는 `IS DISTINCT FROM 'finish'` 검사가 참이어서 예외를 발생시킨다.

## `IS DISTINCT FROM`: `NULL`까지 안전한 다름 비교

```sql
IF parent_type IS DISTINCT FROM 'finish' THEN
  RAISE EXCEPTION 'finish_detail parent must be a finish trait';
END IF;
```

결과는 다음과 같다.

| `parent_type` | 비교 결과 |
|---|---|
| `'finish'` | `false` |
| 다른 문자열 | `true` |
| `NULL` | `true` |

일반적인 `parent_type <> 'finish'`는 `parent_type`이 `NULL`이면 `true`나 `false`가 아니라 `unknown`을 반환한다. 그러면 `IF` 본문으로 들어가지 않아 부모 행이 없는 경우를 놓칠 수 있다.

이 마이그레이션에서는 부모 조회 결과가 없어서 `parent_type = NULL`이어도 잘못된 부모로 판단해 예외를 내야 하므로 `IS DISTINCT FROM`이 알맞다.

### MSSQL과 비교

SQL Server 2022 이상은 같은 문법을 지원한다.

```sql
IF @parent_type IS DISTINCT FROM 'finish'
BEGIN
    THROW 50000, 'finish_detail parent must be a finish trait', 1;
END;
```

이전 SQL Server에서는 보통 다음처럼 풀어 쓴다.

```sql
IF @parent_type <> 'finish' OR @parent_type IS NULL
BEGIN
    THROW 50000, 'finish_detail parent must be a finish trait', 1;
END;
```

즉 `IS DISTINCT FROM`은 값이 다르거나 한쪽만 `NULL`인 경우를 한 번에 검사하는 NULL-safe 비교다.

## `EXCLUDED`: 중복 때문에 INSERT되지 못한 새 행

```sql
INSERT INTO traits (type, slug, label_kr, ...)
VALUES ('form', NEW.slug, NEW.label_kr, ...)
ON CONFLICT (type, slug) DO UPDATE
SET
  label_kr = EXCLUDED.label_kr;
```

`EXCLUDED`는 `INSERT ... ON CONFLICT DO UPDATE` 안에서 PostgreSQL이 제공하는 특별 이름이다. 고유 제약 충돌 때문에 그대로 INSERT되지 못한, 이번에 넣으려고 한 새 행을 가리킨다.

예를 들어 DB에 이미 다음 행이 있다고 하자.

```text
type=form, slug=liquid, label_kr=리퀴드
```

이번 INSERT 값이 다음과 같으면 `(type, slug)`가 중복된다.

```text
type=form, slug=liquid, label_kr=액상
```

이때:

- 기존 대상 행의 `label_kr`: `리퀴드`
- `EXCLUDED.label_kr`: 이번에 들어온 `액상`

따라서 `label_kr = EXCLUDED.label_kr`는 기존 행을 `액상`으로 갱신한다.

MSSQL의 `MERGE`로 비유하면 `EXCLUDED`는 대체로 `source` 별칭 역할과 비슷하다.

```sql
MERGE traits AS target
USING (...) AS source
ON target.type = source.type
AND target.slug = source.slug
WHEN MATCHED THEN
  UPDATE SET target.label_kr = source.label_kr;
```

정리:

- 기존 DB 행: 충돌한 대상 행
- `EXCLUDED.column`: 이번에 INSERT하려던 새 값
- `ON CONFLICT ... DO UPDATE`: 중복이면 실패 대신 기존 행 갱신

## `FOUND`: 직전 SQL이 행을 처리했는지

`FOUND`는 PL/pgSQL이 자동으로 제공하는 boolean 변수다. 바로 직전 SQL 문이 행을 하나 이상 찾거나 변경했으면 `true`, 아니면 `false`가 된다.

이 마이그레이션의 흐름:

```sql
UPDATE traits
SET
  slug = NEW.slug,
  label_kr = NEW.label_kr,
  ...
WHERE type = 'finish'
  AND slug = OLD.slug;

IF FOUND THEN
  RETURN NEW;
END IF;
```

- 기존 mirror 행을 `UPDATE`함: `FOUND = true` → trigger 함수 종료
- 조건에 맞는 행이 없음: `FOUND = false` → 아래 `INSERT ... ON CONFLICT` 실행

즉 먼저 기존 행을 갱신해 보고, 없을 때만 새 행을 만드는 분기다.

MSSQL로 비유하면 다음과 비슷하다.

```sql
UPDATE traits
SET ...
WHERE type = 'finish'
  AND slug = @old_slug;

IF @@ROWCOUNT > 0
    RETURN;
```

주의할 점은 `FOUND`가 특정 SQL에 묶여 있는 이름이 아니라, SQL을 실행할 때마다 다시 바뀌는 상태값이라는 것이다. 따라서 확인하려는 SQL 바로 다음에 읽어야 한다.
