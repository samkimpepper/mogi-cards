# PR #51 — 미래 할 일 읽기부터 생성·수정 구조와 시험 경계까지

모기는 도수치료 가는 길에 다이소에 들러. 그런데 도수치료는 내일인데 다이소 할 일은 오늘로 잡혀 있었어. 투두냥이 이 어긋남을 찾으려면 Calendar 일정과 함께 **미래에 예약된 Things 할 일**을 읽을 수 있어야 해.

이번 PR은 그 목록을 가져오는 `things:upcoming`을 추가해. 읽은 목록을 보고 날짜 변경을 판단하는 건 투두냥이고, 실제 변경은 기존 `things:add` 명령을 별도로 실행해서 해. Upcoming 명령 자체가 Calendar와 비교하거나 할 일 날짜를 고치지는 않아.

이 노트는 한꺼번에 큰 호출 트리를 외우지 않고 **두 갈래의 입구 → 함수 안의 큰 흐름 → 공용 날짜 계산 → 시험** 순서로 펼쳐 보는 읽기 화면이야. 각 절 끝에는 짧은 주관식 퀴즈가 있어. 설명을 다시 보면서 한두 문장으로 써도 되고, 막히면 헷갈리는 부분만 적어도 돼. 3번과 5번은 연습용으로 만든 잘못된 리뷰 댓글에 답하는 문제야. 답과 해설은 미리 넣지 않았어. 코드 흐름과 테스트는 서로 다른 구간이니, 한 번에 다 읽을 필요는 없어.

문항은 [주관식 이해 체크 가이드](../../guide-subjective-checks.md)를 따라 만들었어. 답을 쓴 뒤 채점을 요청하면 **정답 / 부분 이해 / 다시 보기**로 구분하고, 맞은 부분·빠진 핵심·오해한 경계를 짚을게. 함수 이름을 똑같이 외웠는지보다 사건의 원인과 결과를 연결했는지로 볼 거야. 모든 문항을 채워야 읽기를 마칠 수 있는 건 아니야.

## 1. 첫 지도 — 읽기와 생성·수정의 입구

**현재 위치: 투두냥이 어떤 명령을 실행하는지 보는 단계.** 여기서 수정은 `things:add`가 같은 제목의 기존 할 일을 재사용하는 경우를 말해. 다른 제목 변경·태그 변경 명령 전체를 그린 지도는 아니야.

```text
투두냥
│
├─ “내일부터 사흘 동안 예약된 할 일을 보여줘”
│
│   things:upcoming
│        ↓
│   bin/things-upcoming.js
│   명령 입력을 받는다
│        ↓
│   readUpcoming()                  [src/upcoming.js]
│   미래 할 일을 읽는 과정을 진행한다
│        ↓
│   날짜 범위 + 할 일 목록 반환
│
└─ “다이소 할 일을 내일로 잡아줘”

    things:add
         ↓
    bin/things-add.js
    명령 입력을 받는다
         ↓
    addTodo()                       [src/add/add-todo.js]
    새 할 일을 만들거나 기존 할 일을 수정한다
         ↓
    처리 결과 + 확인한 내용(summary) 반환
```

두 함수가 서로를 호출하지는 않아. **목록을 읽은 뒤 변경이 필요하다고 판단하는 주체는 투두냥**이고, 그때 생성·수정 명령을 별도로 실행해. 같은 시점의 한 호출 스택이 아니라, 두 명령을 나란히 놓은 호출 지도야.

## 2. 한 층 펼치기 — readUpcoming과 addTodo 나란히

**현재 위치: 두 함수가 맡은 일의 순서를 비교하는 단계.** 각 열은 위에서 아래로 읽어. 좌우의 같은 줄이 동시에 실행되거나 서로 대응하는 한 단계라는 뜻은 아니야. 입력 검증·전송 방식별 분기 같은 세부는 접어둔 그림이야.

```text
readUpcoming()                         addTodo()
[src/upcoming.js]                      [src/add/add-todo.js]
미래 할 일 읽기                         할 일 생성·수정
│                                      │
├─ ① 읽을 날짜 범위 정하기              ├─ ① 같은 제목의 할 일 찾기
│                                      │
├─ ② Things에서 목록 읽기               ├─ ② 새 생성 / 기존 수정 결정
│                                      │
├─ ③ 받은 문자열을 객체로 바꾸기         ├─ ③ 미리보기 구성
│                                      │     --apply 없으면 여기서 반환
├─ ④ 조건에 맞는 할 일 선별·정렬         │
│                                      ├─ ④ 필요하면 기존 Notes 읽기
└─ ⑤ 날짜 범위와 할 일 목록 반환         │     쓰기 전 값을 기억해두기
                                       │
                                       ├─ ⑤ Things에 생성·수정 요청
                                       │
                                       ├─ ⑥ 저장된 값을 다시 읽어 확인
                                       │
                                       └─ ⑦ 처리 결과와 summary 반환
```

`addTodo()`도 쓰기 전후에 읽어. 같은 읽기라도 가져오려는 값과 목적이 달라.

| 읽는 곳 | 왜 읽나 |
| --- | --- |
| `readUpcoming()` | 투두냥이 판단할 미래 할 일 목록을 얻으려고 |
| `addTodo()`의 쓰기 전 | 어느 할 일을 수정할지, Notes 생략 시 보존할 기존 값이 무엇인지 알아내려고 |
| `addTodo()`의 쓰기 후 | 요청한 날짜·Notes·소속 등이 저장됐는지 확인하려고 |

`addTodo()`의 대상 선택 결과가 없으면 `create`, 1개면 `reuse`야. 같은 제목 후보가 여러 개면 쓰기 전에 멈춰. 날짜·시각·저녁은 같은 파이프라인을 지나고, 실제 보내는 방식과 저녁 칸 추가 확인에서 갈라져.

## 3. 공용 날짜 계산 — 같은 일을 하니까 함께 쓰되, 소속은 분리

**현재 위치: 두 흐름이 서울 기준 오늘 날짜를 쓰는 지점.** 읽기에서는 내일부터 며칠인지 계산하고, 생성·수정에서는 Today·저녁 요청의 저장 날짜가 오늘인지 확인해야 해.

```text
readUpcoming()                         addTodo()
│                                     │
└─ upcomingWindow()                   └─ verifyTodoValues()
   읽을 날짜 범위 계산                    저장된 날짜 확인
   │                                     │
   │                                     └─ expectedDate()
   │                                        Today·저녁 요청이면
   ↓                                        ↓
seoulToday()                           seoulToday()
           같은 함수, src/seoul-date.js 소속
```

`seoulToday(now)`는 주어진 시각에서 서울 날짜 문자열만 계산해. 이 함수를 호출한다고 Things를 읽거나 수정하지는 않아. 구체 날짜 요청은 그 날짜를 비교하고, Anytime·Someday의 기대 날짜는 `null`이므로 위의 `seoulToday` 호출은 Today·저녁 조건에서 일어나.

### 우리가 발견한 이전 연결과 최종 수정

아래 화살표는 **함수 호출이 아니라 import 의존 관계**야.

```text
처음 b3da91b                         최종 27817e5

upcoming.js                         upcoming.js ──────────┐
  └─ add/verifiers.js                                  ↓
       └─ things-db.js                          seoul-date.js
                                                       ↑
                                    add/verifiers.js ──┘
```

처음에는 읽기 명령이 날짜 계산 하나를 쓰려고 생성·수정 후 검증 파일을 가져왔어. 그 검증 파일은 DB 관련 모듈도 가져오므로, 읽기 기능의 모듈 로딩이 그쪽과 연결됐지. **import만으로 실제 DB를 열거나 add 파이프라인을 실행한 것은 아니야.** 우리가 수정해 달라고 한 건 공용 날짜 계산의 소속이었어.

사건과 기대 결과를 먼저 놓으면 다음과 같아.

| 바라는 관계 | 최종 구현 |
| --- | --- |
| 읽기와 생성·수정이 같은 서울 날짜 계산을 사용 | 둘 다 `seoul-date.js`를 import |
| 읽기가 날짜 하나 때문에 add 검증 담당을 가져오지 않음 | `upcoming.js`에서 `add/verifiers.js` import 제거 |
| 날짜 계산 결과는 유지 | 기존 계산 함수를 공용 파일로 이동 |

아래는 `b3da91b → 27817e5`, `integrations/things/src/upcoming.js`의 **실제 raw hunk 전체**야.

```diff

-import { seoulToday } from "./add/verifiers.js";
 import { dateOnly } from "./open.js";

```

최종 SHA의 import 원문과 위 그림을 대응시키면 이래. 왼쪽 코드는 각 파일의 원본 한 줄 발췌야.

| 원본 코드 | 소속 파일·그림에서의 의미 |
| --- | --- |
| `import { seoulToday } from "./seoul-date.js";` | `src/upcoming.js:5` — 읽기 담당이 공용 날짜 파일을 직접 가져옴 |

## 4. 잘못된 입력 시험 — 정상 코드가 제대로 거절하면 통과

**현재 위치: `upcoming.test.js`가 정상 제품에 어떤 입력을 넣는지 보는 단계.** 투두냥이 범위 밖 날짜 수를 주면 Things를 읽기 전에 거절해야 하고, 앱에서 받은 데이터가 깨졌다면 정상 목록처럼 돌려주지 않아야 해.

| 시험에서 만든 입력·상황 | 기대 결과 | 현재 시험 위치 |
| --- | --- | --- |
| `0`, `15`, `-1`, `2.5`, `3일`, 빈 문자열 등 | `parseDays`가 1~14 범위 오류 | `upcoming.test.js:17-23` |
| 열 수가 틀린 행, 알 수 없는 kind·status | 예상하지 못한 행 오류 | `:90-93` |
| 같은 ID가 두 번 나옴 | 중복 ID 오류 | `:94` |
| `2026-02-30` | 잘못된 날짜 오류 | `:95` |
| Mac 시간대가 UTC | 시간대 오류, 가짜 읽기 호출이 늘지 않음 | `:99-108` |

현재 SHA의 `integrations/things/test/upcoming.test.js:17-24` 원본 발췌야.

```js
test("--days defaults to 3 and accepts only whole numbers from 1 to 14", () => {
  assert.equal(parseDays(undefined), 3);
  assert.equal(parseDays("1"), 1);
  assert.equal(parseDays("14"), 14);
  for (const value of ["0", "15", "-1", "2.5", "3일", "", " 3", "1e1"]) {
    assert.throws(() => parseDays(value), /1 to 14/, value);
  }
});
```

이 시험은 일부러 잘못된 입력을 줘. **제품 함수가 원하는 이유로 오류를 던지면 시험이 통과**해. 제품 함수의 오류와 테스트 전체의 실패는 다른 일이야.

## 6. 보강 제안 — 내부 함수를 따라 부르지 않고 명령의 행동을 보기

모기의 질문 원문:

> “테스트코드는 너무 비즈니스코드에 깊게결합?이되어있음안되자나. 서비스코드 테스트한다치면 서비스에서 호출하는거 하나하나 똑같이 테스트코드에서도 호출하는게아니라”

추가할 시험은 **실제 사용 입구인 명령에 `--days 15`를 넣고 결과와 외부 접촉을 관찰**하면 돼. 내부에서 `parseDays`라는 함수를 호출했는지, 어떤 순서로 도우미 함수를 거쳤는지를 검사할 필요는 없어.

| 제품 구현을 바꾼 경우 | 보강할 명령 시험이 요구할 행동 |
| --- | --- |
| 계속 `parseDays`로 검증 | 범위 오류·실패 종료·읽기 없음이면 통과 |
| 다른 함수나 명령 내부에서 같은 검증 | 같은 행동이면 통과 |
| 검증 자체를 생략해 15일 읽기 진행 | 실패해야 함 |

**위 표는 아직 작성하지 않은 보강 시험의 기대 동작이야. 실제로 현재 시험을 돌린 결과는 5절의 표와 구분해야 해.** 이번 과외에서는 새 회귀 시험을 제품에 추가하지 않았어. 명령을 직접 비교해 관찰한 결과를 토대로 어떤 조건을 확인하면 되는지 제안한 거야.

“읽기 0회”는 외부 앱에 접촉하지 않는다는 약속을 보는 것이고, 내부 함수 호출 횟수나 이름을 고정하는 검사는 아니야. `parseDays` 단위 시험도 계속 쓸모가 있지만 그것만으로 명령 입구의 연결까지 증명되지는 않아.

이 구간에서 모기는 “근데 검증 없이 그대로진행했을때 테스트가 실패면 이게 맞는거아니야? 고칠데가더있나”라고 재확인했어. 과외냥이가 미래 보강 시험의 기대 결과와 현재 시험의 실제 결과를 흐리게 설명했던 문제였고, 현재의 고장 사본은 **8개 모두 통과했다**는 사실로 바로잡았어.
