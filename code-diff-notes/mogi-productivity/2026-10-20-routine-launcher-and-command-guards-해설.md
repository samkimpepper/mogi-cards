## 루틴 JS는 레포에 남고, 작은 앱이 그 파일을 실행한다

모기가 같은 경로의 루틴 JS를 수정하면 다음 실행에서 수정된 파일을 읽는다. JS를 Homebrew 폴더에 복사하는 구조가 아니다. 앱을 만드는 시점과 매일 루틴을 실행하는 시점은 다르다.

모기 질문:

> 아 그렇구나 그럼 holiday-routine.js의 경로가바뀌면 여기도 수정해야하는거네 그리고 저 routineScriptPath함수안의 join도 마찬가지고

`integrations/routine/src/launcher.js`의 `routineScriptPath()`는 앱 빌드에서 사용할 JS 경로를 만든다. 빌드 명령은 C 실행기를 컴파일하고 서명한다. 예약 시각에는 macOS의 launchd가 앱을 실행하고, C 실행기가 자식 Node에 고정된 레포 JS 경로와 `--apply`를 전달한다. 같은 위치의 JS 내용만 바꾸는 경우와 JS 경로를 바꿔 실행기를 다시 만드는 경우를 구분한다.

| 명령 | 실제로 반영하는 대상 |
|---|---|
| `pnpm routine --apply` | 조건에 따른 Things 루틴 변경 |
| `pnpm routine:launcher build --apply` | 실행기 앱 생성·서명 |
| `pnpm routine:schedule install --apply` | 예약 등록 |
| `launchctl kickstart …` | 등록된 예약을 지금 실행. 이 실행기는 실제 반영 인자를 사용함 |

정확한 즉시 실행 명령·로그 확인은 제품 루틴 README가 정본이다. 이 해설의 축약 명령을 실행용 복사본으로 쓰지 않는다.

## 코드 서명의 목적과 필요한 환경만 전달하는 이유

모기 질문:

> 이게 최초에 시작된 이유가뭘까? 어떤 사고가터져서.. 어떤문제때문에(구체적으로) 인증서. 머 서명 이런걸 하게된거냐옹

정상 프로그램 이름·버전만으로 받은 파일의 제작자와 변경 여부를 보증할 수 없다. 1994년 ircII 악성 배포본 사고는 이 필요성을 보여주는 실제 사례로 설명했다. 서명 기술이 그 사고에서 처음 발명됐다는 뜻은 아니다. [당시 CERT 공지](https://groups.google.com/g/comp.security.announce/c/7NhX_aDgrZU)

코드 서명은 코드 변경 검증의 근거를 제공하고, 개발자 인증서는 공개키와 개발자 신원을 연결한다. ad-hoc 서명은 인증된 개발자 신원을 제공하지 않는다. 서명·인증서 확인과 파일 접근 권한 부여도 서로 다른 단계다. 이번 실행기는 Node 업데이트와 권한 귀속 대상인 작은 앱의 변경을 분리하려는 구조이며, 모든 운영 상황에서 권한 창이 사라졌다고 검증한 것은 아니다.

PR #37 리뷰 반영에서는 자식 Node에 물려주던 전체 `environ` 대신, 계정 정보로 정한 HOME과 고정 PATH만 새 `child_env` 배열로 전달했다. `integrations/routine/launcher/main.c`가 Node를 `posix_spawn()`으로 실행할 때 이 배열을 사용한다.

모기 연결:

> 그냥 커스텀객체만들어서(약간 엔티티 생으로 리턴하는게아닌 DTO만드ㅡㄴ 그런느낌ㅋ) 하는것이군!

이 비유는 원본 전체 대신 필요한 항목만 골라 새 구조를 전달한다는 점에 해당한다. 실행기 자신의 main 이전 동적 라이브러리 주입은 자식 환경 배열만으로 막을 수 없어 서명의 Hardened Runtime 옵션으로 별도 다뤘다.

보고된 검증은 최소 환경·주입 차단과 새 서명의 임시 앱 권한 귀속 확인이다. 과외냥이는 해당 시험을 재실행하지 않았고, 실제 운영 설치 후 전체 디스크 접근·예약 실행의 결과를 확인한 것으로 넓히지 않는다.

## 운영 PR #7은 명령에 적힌 대상과 실제 실행 대상을 확인한다

모기 질문:

> 깃환경변수, bash literal_argv, 심링크 이거 실제 code diff랑 같이 좀만더설명해줘ㅠ

이 절은 별도 저장소 todo-ops의 `scripts/todo-scoped-hook.py`를 다룬다. Claude의 Bash 실행 전 검사이며, 제품 실행기 C 코드와 같은 파일·기능이 아니다.

| 검사 | 확인하려는 차이 | `d0d16a1`에서의 상태 |
|---|---|---|
| Git 환경변수 | 명령에 적힌 폴더 외에 저장소·작업 경로·설정을 바꾸는 입력이 있는가 | 남음. 지정 목록이 있거나 허용되지 않은 설정이면 예외를 주지 않음 |
| `literal_argv()` | Bash가 `$()` 등을 해석해 원문과 다른 실행을 만드는가 | 남음. 보수적인 문자 제한을 적용함 |
| 경로 `resolve()`와 링크 검사 | 다른 경로처럼 보여도 보호 대상과 같은 실제 경로인가 | worktree 삭제 예외와 함께 제거됨 |

모기 재확인:

> 그러니까 머 $가들어가면 무조건차단인건가

이 함수에서는 따옴표 안팎 모두 `$`를 거부한다. 안전하게 글자로 쓸 수 있는 모든 셸 표현을 허용하려는 분석기가 아니라, 좁게 인정할 명령 형태만 받는 검사다. 거부는 이 예외를 통한 허용을 포기하고 기존 가드로 넘긴다는 뜻이며, 모든 명령이 즉시 무조건 차단된다는 뜻은 아니다.

심볼릭 링크는 대상 경로를 저장해서 여러 경로에서 같은 파일·폴더를 사용할 수 있게 한다. 이 Mac의 `/opt/homebrew/bin/node`가 버전별 실제 Node를 가리키는 것이 직접 확인한 예다. 링크가 가리키는 버전을 바꾸면 호출자의 고정 경로를 유지할 수 있다. 권한 검사에서는 이름이 다른 두 경로가 실제로 같은 대상을 가리킬 가능성도 확인해야 한다. [GNU 설명](https://www.gnu.org/software/coreutils/manual/html_node/ln-invocation.html)

현재 PR #7에 남긴 업무는 main의 `pull --ff-only origin main` 예외다. worker-reap은 pull을 하지 않으며, 작업 정리는 기존 버그 `td-2zs`/원본 #178 수리 뒤 해당 도구를 사용하고 그 전에는 모기가 직접 실행한다는 담당자 보고·계약을 확인했다. 이는 버그 수리나 재사용 통합의 완료 확인이 아니다.
